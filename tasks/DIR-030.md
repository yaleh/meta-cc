## Finding

The current MCP surface can search normalized content but lacks a metadata-first Codex session query and an exact `session_id` selector. `scope=session` means "most recent session" rather than an explicit Codex thread. Project queries load every matching rollout before jq filtering. Archived state, source kind, model provider, subagent lineage, thread status, title, and updated time are not first-class filters.

This makes targeted queries expensive and creates ambiguity between project scope, latest-session scope, and exact-thread scope.

## Dependency

Depends on DIR-029 so session discovery uses one backend-neutral contract across app-server and offline files.

## Proposal

Add a consolidated metadata-first MCP query for sessions and extend content/signal queries with precise Codex selectors. Preserve all existing defaults, especially Claude-only behavior when `provider` is omitted.

## Contract

- Add `query_sessions` or an equivalently consolidated mode that returns thread metadata without loading turns.
- Add exact `session_id` filtering to content, signal, timeline, and analysis paths where applicable.
- Support filters for cwd, archived, source kind, model/model-provider, status, parent/ancestor thread, created/updated time, title search, and include-internal/subagent behavior.
- Cursor pagination is stable and ordering is deterministic.
- `scope=session` remains backward compatible but documentation distinguishes it from exact `session_id`.
- Invalid or unsupported filters fail closed with actionable errors.
- A failure to load one session becomes a per-session warning when other sessions can still satisfy a project query.

## Plan

1. Define the session metadata response and shared filter structure.
2. Add schemas and strict argument validation for the new selectors.
3. Push supported filters into app-server/SQLite listing before deep turn loading.
4. Add exact-session fast paths that call `GetSession`/`thread/read` directly.
5. Make multi-session loading tolerate isolated corrupt/missing sessions with structured warnings.
6. Update MCP reference docs, examples, and cross-provider compatibility tests.

## Acceptance Criteria

- [ ] Listing session metadata does not parse rollout contents.
- [ ] Exact session lookup reads only the requested thread.
- [ ] Project and session scope cannot cross cwd boundaries.
- [ ] Archived, exec, alternate-provider, and subagent filters have fixture coverage.
- [ ] One corrupt rollout does not erase valid results from other sessions.
- [ ] Existing Claude-default schemas and results remain compatible.

## Definition of Done

- [ ] Tool schemas, handlers, docs, and tests describe the same filters.
- [ ] Query planning demonstrates metadata filtering before deep loading.
- [ ] `make commit` passes.

Build (worktree `/home/yale/work/meta-cc-worktrees/DIR-030`, branch

fresh-context adversarial auditor found and reproduced a real cross-project data
leak in the new `session_id` fast path — this is a security-relevant correctness
bug, not just a spec gap.

**AC violated**: "Project and session scope cannot cross cwd boundaries."

**Root cause**: `ExecuteQueryForSession` (`internal/mcp/executor/provider_query.go:60-76`)
branches by provider:
- `provider=="codex"`/`"all"` → `providerrecords.BuildForSession`, which correctly
  checks `session.CWD != projectPath` and excludes/warns on mismatch (tested:
  `TestBuildForSession_CWDBoundaryExcludesCrossProjectSession`).
- `provider==""`/`"claude"` (the DEFAULT, most-used path) → instead calls
  `locator.NewSessionLocator().FromSessionID(sessionID)`
  (`internal/mcp/executor/provider_query.go:66`), which does a global
  `{session_id}.jsonl` search across ALL project-hash directories on disk with
  **zero comparison against the caller's `working_dir`/cwd**. Its own pre-existing
  test `TestFromSessionID_MultipleProjects` already documents that it returns
  whatever it finds (newest by mtime on collision) without project filtering.

This `session_id` parameter is wired into every consolidated content/signal
handler (`handleQuerySessionContent`, `handleQueryUserMessages`, `handleQueryTools`,
`handleQueryToolErrors`, `handleQueryTokenUsage`, `handleQueryConversationFlow`,
`handleQuerySystemErrors`, `handleQueryFileSnapshots`, `handleQueryToolBlocks`,
`handleQueryTimestamps`) — none of them cwd-check the resolved session on the
Claude/default path.

**Reproduced**: auditor built a scratch test creating a Claude session file under a
`project-x` hashed directory, then called `handleQueryUserMessages` with
`working_dir` mapping to `project-y` and `session_id` pointing at the project-x
session. Result: no error, 1 entry returned containing project-x's content —
confirming a caller who knows (or guesses/enumerates) a `session_id` can read another
project's session content by passing an unrelated `working_dir`.

**Coverage gap confirming this was untested, not merely unfixed**: the diff's own
new `session_id` fast-path tests (`session_id_fastpath_test.go`,
`query_sessions_handler_test.go`) all pass `"provider": "codex"` explicitly — no
test anywhere exercises `session_id` on the default/Claude provider path, so the
missing boundary check was never exercised.

**Not the basis of this verdict (checked clean)**: tool-count bump 15→16 is
internally consistent across all doc/config locations; `records.Build`'s per-session
corrupt-rollout tolerance is real and tested; the `check-no-scanner` flag on
`appserver/client.go:90` predates this branch (confirmed via `git log`, present
already at DIR-029's landed commit `65bcb7a`).

**Suggested fix direction** (not applied — routing to human per no-retry-loop
policy): `ExecuteQueryForSession`'s Claude/default branch needs the same cwd-boundary
check `BuildForSession` already does for Codex — either resolve the session via
`FromSessionID` and then verify its project/cwd matches the caller's `working_dir`
before returning (excluding + warning on mismatch, consistent with the Codex path's
behavior), or constrain the lookup to the caller's own project-hash directory instead
of searching globally.
