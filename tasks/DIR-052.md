# `.github/workflows/release.yml` and `tests/validation/validate-artifacts.sh` still hand-duplicate the dead LDFLAGS path DIR-049 just fixed

## Finding

DIR-049 (commit `c6fc1f8`) fixed `Makefile`'s LDFLAGS to target the real
`github.com/yaleh/meta-cc/internal/version.Commit`/`.BuildTime` symbols instead of the nonexistent
`github.com/yaleh/meta-cc/cmd.*` path, for `make build`/`make install`/`make cross-compile`.

DIR-049's adversarial audit (fresh-context, independently reproduced) found that two other places in
this repo hand-duplicate the *old, still-broken* LDFLAGS string rather than reusing the Makefile's
(now-fixed) `LDFLAGS`/`LDFLAGS_VALUE` variable:

- `.github/workflows/release.yml:44` — the actual GitHub Actions release pipeline that builds the
  binaries shipped in GitHub Release tarballs (what `install.sh`/an end user's release-tarball
  install actually gets) constructs its own `-ldflags` string pointing at
  `github.com/yaleh/meta-cc/cmd.Version`/`.Commit`/`.BuildTime` — the same dead path DIR-049 fixed
  in the Makefile, but not fixed here.
- `tests/validation/validate-artifacts.sh:83` — likewise hand-duplicates the same dead
  `github.com/yaleh/meta-cc/cmd.*` LDFLAGS path.

Since these two locations were not touched by DIR-049 (its Acceptance Criteria was scoped to
`make install`/`make cross-compile`/`make build`, which now correctly use the fixed
`internal/version.Commit`/`.BuildTime` path), any binary produced by the actual release pipeline —
i.e. what most real end users install via `install.sh` or a downloaded release tarball, as opposed
to `make install-user` built from a source checkout — will still silently embed no real commit hash
or build timestamp, for the exact same reason DIR-049 diagnosed: Go's `-X` linker flag is a silent
no-op when its target symbol doesn't exist.

This is the same defect class DIR-049 fixed, recurring via copy-paste duplication rather than a
single source of truth for the LDFLAGS string.

## Proposal

1. In `.github/workflows/release.yml`, replace the hand-duplicated `-ldflags "..."` string with a
   call to the Makefile's own `print-ldflags-value` target (added in DIR-049) or an equivalent
   `make`-driven build step, so the release pipeline can never drift from the Makefile's LDFLAGS
   again.
2. Do the same in `tests/validation/validate-artifacts.sh` — replace its own hand-duplicated LDFLAGS
   string with a call to `make print-ldflags-value` (or build via `make build`/`make cross-compile`
   directly rather than a raw `go build -ldflags "..."` invocation).
3. Add a regression check (a shell grep/lint, or extending DIR-049's `TestLDFLAGSCommitAndBuildTimeAreWired`-style
   test) that fails if any file in the repo other than `Makefile` itself hardcodes an
   `-X github.com/yaleh/meta-cc/...Commit=`/`.../BuildTime=` string, to prevent this exact class of
   drift from recurring a third time.

## Acceptance Criteria

- [ ] `.github/workflows/release.yml`'s build step no longer hand-constructs its own `-ldflags`
      string; it derives the LDFLAGS from the Makefile (e.g. `make print-ldflags-value` or an
      equivalent `make`-driven build invocation).
- [ ] `tests/validation/validate-artifacts.sh` likewise no longer hand-constructs its own LDFLAGS
      string.
- [ ] A binary built via the (locally-simulated) release workflow's actual build command embeds a
      non-"unknown" commit matching `git rev-parse --short HEAD`, verified by an actual run.
- [ ] `grep -rn "github.com/yaleh/meta-cc/cmd\.\(Version\|Commit\|BuildTime\)" .` (excluding
      `Makefile` itself and this task's own file) returns no hits, confirming no other
      hand-duplicated dead-path LDFLAGS string remains.
- [ ] `make commit` passes.

## Definition of Done

      the single Makefile source of truth, not a hand-duplicated string.
