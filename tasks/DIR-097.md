## Finding

Dogfooding session (2026-07-30): analyzing this project's own 2-day task-execution history with meta-cc's MCP tools, a consumer called `query_session_signals(type="errors")` and received raw user-role JSONL records. `toolUseResult` is a string in some records and an object in others; the actual error text is nested inside `message.content[].content`. The consumer's first jq extraction attempts returned nothing because the shape is undocumented and irregular — the raw JSONL had to be inspected by hand to extract error texts.

CLAUDE.md's docs describe role=tool "block fields", but the errors signal's actual shape differs from what a consumer builds from that guidance. This is a projection gap: the signal tool passes raw record variance through instead of normalizing to a contract the docs can promise.

## Dependencies

None.

## Scope

owner_repo: meta-cc

Project every error record to a stable shape regardless of the underlying `toolUseResult` string/object variance. Keep raw access available behind an opt-in flag for consumers that need it. No change to how errors are collected or categorized — only the output projection and its documentation.

## Plan

1. Locate the errors-signal extraction path in `internal/query/`; enumerate the `toolUseResult` string and object variants present in this project's corpus.
2. Project every error record to `{timestamp, session_id, tool_name, error_text, category}`, handling both variants and the nested `message.content[].content`.
3. Derive `category` with the same labels `analyze_errors` categorization uses, so the two tools agree.
4. Add an opt-in flag (e.g. `raw=true`) that preserves the original record for consumers that need it.
5. Document the exact projected shape in `docs/guides/mcp-query-tools.md` with a working jq example; add the pattern to `docs/guides/two-stage-query-guide.md`.
6. Add tests covering string-variant and object-variant records against this project's corpus.

## Implementation notes

The errors path lives in `internal/mcp/executor/handlers.go`
(`handleQueryToolErrors`), not `internal/query/` — no error extraction exists in
that package. The pure projection lives in the new
`internal/mcp/executor/error_projection.go`; `internal/mcp/tools/tools.go`
documents the new `raw` parameter on the `query_session_signals` schema.

`tool_name` is not on the error record at all, so it is resolved with a second
pass over assistant `tool_use` records correlated by `tool_use_id` (the only key
carried by both the raw Claude and the normalized cross-provider record
families); a failed join degrades to an empty `tool_name` + warning rather than
failing the query. `error_text` reuses `internal/types.ToolResult`'s
string-or-text-block extraction so `analyze_errors` sees the same text;
`category` is `analyzer.ClassifyErrorType(tool_name, error_text)` — the exact
call `analyze_errors` labels its `by_type` groups with.

Corpus evidence (this project's own sessions, 31 error records): every projected
record carried exactly the five fields, `tool_name` resolved on all 31
(`Bash`/`Read`/`Edit`), and category counts `bash_exit_code` 16 /
`uncategorized` 15 matched `analyze_errors`' `by_type` on the same corpus
exactly.
