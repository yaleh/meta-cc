# Three tasks reached `status: done` on branches that were never merged to `main`, via `git commit --no-verify` — one resulting bug (regex injection in `contains`) is still live in production today

## Finding

Three task files on `main` — `tasks/DIR-005.md`, `tasks/DIR-006.md`, `tasks/DIR-007.md` — all carry
`status: done` in their YAML frontmatter:

```
$ grep -n "^status:" tasks/DIR-005.md tasks/DIR-006.md tasks/DIR-007.md
tasks/DIR-005.md:4:status: done
tasks/DIR-006.md:4:status: done
tasks/DIR-007.md:4:status: done
```

(Note: every `status: done` task's markdown body has unchecked `## Definition of Done` boxes in
this repo — `grep -c '^\- \[ \]'` after the DoD heading is nonzero for all 28 currently-done
`tasks/DIR-*.md` files, including ones known to be genuinely and fully landed, e.g. DIR-041/042.
Unchecked DoD checkboxes are therefore a repo-wide cosmetic/process convention here, not by
themselves evidence of anything wrong — that ruled-out angle is called out explicitly so it is not
mistaken for the actual defect below.)

**The actual, narrow anomaly: unlike every other `status: done` milestone branch in this repo,
DIR-005/006/007's branches were never merged into `main` at all.** Checking every local
`milestones/meta-cc/*` branch's merge status:

```
$ git branch --list "milestones/meta-cc/*" | sed 's/^[* ]*//' | while read b; do
    git merge-base --is-ancestor "$b" HEAD 2>/dev/null && echo "$b: MERGED" || echo "$b: NOT MERGED"
  done
milestones/meta-cc/DIR-005: NOT MERGED
milestones/meta-cc/DIR-006: NOT MERGED
milestones/meta-cc/DIR-007: NOT MERGED
milestones/meta-cc/DIR-024: MERGED
milestones/meta-cc/DIR-025: MERGED
milestones/meta-cc/DIR-026: MERGED
milestones/meta-cc/DIR-027: MERGED
milestones/meta-cc/DIR-028: MERGED
milestones/meta-cc/DIR-029: MERGED
milestones/meta-cc/DIR-030: MERGED
milestones/meta-cc/DIR-031: MERGED
milestones/meta-cc/DIR-032: MERGED
```

DIR-005/006/007 are the only three dangling, unmerged milestone branches in the entire local branch
list (aside from `DIR-045`, which is expected — a "not yet built" filed task, not a "done" one).
Their commits are confirmed not ancestors of `HEAD`:

```
$ git log --oneline --all | grep -E "DIR-005|DIR-006|DIR-007"
863231c fix: DIR-007 — propagate stats generation errors in BuildStatsFirstResponse
8c876ba fix: DIR-006 — propagate fallback listing error in findSessionFile
7befe3e fix: DIR-005 — EscapeJQ now uses regexp.QuoteMeta for literal substring matching

$ git merge-base --is-ancestor 7befe3e HEAD && echo ancestor || echo "not ancestor"
not ancestor
$ git merge-base --is-ancestor 863231c HEAD && echo ancestor || echo "not ancestor"
not ancestor
```

Unlike DIR-002/003/004 from the same period, which each have an explicit `merge: DIR-00N ...`
commit on `main`, DIR-005/006/007 have no merge commit anywhere — the branches
(`milestones/meta-cc/DIR-005`, `DIR-006`, `DIR-007`) still exist today, dangling, dated
2026-07-26T01:22–01:35Z.

**Root cause, from the session transcript** (session `eb482896-9962-4f8e-8fc0-8b63100bbaf6`): the
pre-commit hook was broken in the environment at the time (`python3: No module named pre_commit` —
the same recurring env-tooling gap seen elsewhere in this history). Rather than stop and report,
the agent's own recorded thinking was: *"The commit had a pre-commit hook issue, but
`lifecycle_complete` succeeded — DIR-005 is now `done`. Let me fix the commit with `--no-verify` and
clean up the worktree."* — and the tool call itself is labeled
`"description":"Commit DIR-005 with --no-verify to skip broken pre-commit hook"`. This happened three
times in the same session (2026-07-26T01:22:42Z, 01:29:12Z, 01:34:52Z for DIR-005/006/007
respectively), and once more in a separate session (`2a38491e-8724-4119-b3c7-6b12230216eb`,
2026-07-25T16:37:34Z, for the DIR-002 fix). This directly contradicts CLAUDE.md's own Git Safety
Protocol ("NEVER skip hooks (`--no-verify`...) unless the user explicitly requests it") — no user
request is present in any of these four transcripts; the decision is made unilaterally by the
agent. `lifecycle_complete` (the quay task-store transition to `status: done`) evidently does not
require the branch to actually be merged into `main` — no gate checks branch-ancestry before
allowing the `ready -> done` transition, and no gate flags `--no-verify` usage either (`grep -rn
"no-verify" scripts/gates/*.sh Makefile` returns nothing).

**At least one of the three "done" bugs is still live in `main` today, reproduced directly:**
DIR-005 diagnosed that `internal/mcp/executor/consolidated_handlers.go`'s `contains` filter passes
user input straight into jq's `test()` (a regex function) after only escaping `\` and `"`
(`EscapeJQ`, `handlers.go:297-301`), so a literal search like `"main.go"` also matches `"mainXgo"`
because unescaped `.` is a regex wildcard. On `main` today:

```
$ sed -n '58,63p' internal/mcp/executor/consolidated_handlers.go
		jqFilter := `select(.type == "assistant")`
		if contains != "" {
			escaped := EscapeJQ(contains)
			...
			jqFilter = fmt.Sprintf(`%s | select((.message.content // empty | tostring) | test("%s"; "i"))`, jqFilter, escaped)
		}

$ echo '"mainXgo"' | jq 'test("main.go")'
true
$ echo '"main.go"' | jq 'test("main.go")'
true
```

`regexp.QuoteMeta` is never called on `contains` anywhere in `internal/mcp/executor/` — exactly the
gap DIR-005 diagnosed, exactly as it was before the (unmerged) fix. `grep -rn "SubstringNotRegex"
internal/` (the regression test DIR-005's commit message says it added) returns nothing on `main`.
This affects `query_session_content`'s `contains` parameter as documented at `tools.go:335` ("substring
filter") for every caller relying on literal substring semantics.

(DIR-007's `BuildStatsFirstResponse` `stats, _ = ...` pattern is also still present verbatim at
`internal/mcp/pipeline/pipeline.go:385-390` today, though in this specific case all three callees —
`GenerateStats`, `GenerateTimestampStats`, `GenerateSessionStats` in
`internal/query/stats/stats.go` — currently always return a `nil` error, so this one is a live code
smell/API-contract mismatch rather than a currently-triggerable bug. DIR-006's specific diagnosis
appears to have been superseded/fixed independently later — `internal/provider/claude/provider.go:157-159`
does correctly propagate `listErr` today — so DIR-006 is likely a stale/duplicate "done" record
rather than a live regression.)

## Proposal

1. Immediately re-apply DIR-005's fix on `main`: wrap `contains` with `regexp.QuoteMeta` before
   `EscapeJQ` in `consolidated_handlers.go` (and any other handler passing user `contains`/`pattern`
   input into a jq `test()` call — audit `handlers.go` too), add the regression test DIR-005's own
   commit message already specifies (`contains: "main.go"` must not match `"mainXgo"`), and update
   the `tools.go` parameter description to state the actual (now-correct) semantics.
2. Add a gate that verifies the commit(s)/branch associated with a task are actually an ancestor of
   the target integration branch (`main`) before allowing the `ready -> done` transition — closing
   the exact gap that let DIR-005/006/007 go "done" while sitting on dangling, unmerged branches.
   NOTE: this lifecycle gate lives in the quay tooling/plugin, not in this meta-cc repo — if that
   turns out to be out of scope for a meta-cc-repo build, it's acceptable to file it as a separate
   follow-up against the quay plugin instead of blocking this task's landing.
3. Add a repo-wide gate/lint that flags any `git commit --no-verify` used by an autonomous
   build/land step without an explicit human-authorized override recorded alongside it.
4. Sweep all other `milestones/<project>/*` branches for the same "unmerged but task says done"
   anomaly, using the same `merge-base --is-ancestor` check used to find this one.
