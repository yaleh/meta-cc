## Finding

The `contains` parameter in query tools performs regex matching via jq's `test()` function but is documented as substring matching. In `internal/mcp/executor/consolidated_handlers.go:58-63`, the `contains` value is passed to `EscapeJQ` (which only escapes `\` and `"`, defined in `handlers.go:203-207`) and then used in `jq test(regex; "i")`. Regex metacharacters like `.`, `*`, `(`, `[` are NOT escaped. A user searching for `main.go` will match `mainXgo`, `main_go`, etc. because `.` is a regex wildcard. The tool definition at `tools.go:272-273` documents this as "Optional substring filter" but the implementation uses regex.

## Proposal

Add `regexp.QuoteMeta` escaping on the `contains` value before passing to jq's `test()` function, so regex metacharacters are treated as literals. This preserves the regex-based implementation (and its case-insensitive matching) while fixing the false-positive behavior. Update the tool description to clarify matching semantics.

## Plan

1. Fix `internal/mcp/executor/consolidated_handlers.go:59` — wrap the contains value with `regexp.QuoteMeta` before `EscapeJQ`: `escaped := EscapeJQ(regexp.QuoteMeta(contains))`
2. Update tool description at `tools.go:272-273` to document that the match is case-insensitive substring (literal, not regex)
3. Add test case: `contains: "main.go"` should NOT match `mainXgo`
