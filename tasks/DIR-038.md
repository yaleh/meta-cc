## Finding

The repo has a dedicated lint gate, `check-no-scanner` (`Makefile:599-607`), that exists specifically
to ban raw `bufio.NewScanner` usage on line-oriented parsing paths (its default 64KB token limit
silently truncates/errors on long lines). `check-no-scanner` is wired into `lint`
(`Makefile:610: lint: fmt vet lint-errors lint-error-handling lint-markdown check-no-scanner`), which
is in turn wired into `push` (`Makefile:311: push: check-code-quality check-build-quality
check-comprehensive test-all lint build`) — but **not** into `commit`
(`Makefile:297: commit: check-essential test`). That asymmetry matters below.

**The gate is failing right now, independently reproduced today (2026-07-28):**

```
$ export PATH=/usr/local/go/bin:$PATH && make check-no-scanner
Checking for raw bufio.NewScanner on JSONL paths...
internal/provider/codex/appserver/client.go:90:	scanner := bufio.NewScanner(r)
ERROR: Found raw bufio.NewScanner usage. Use parser.ReadLineFiltered instead.
make: *** [Makefile:601: check-no-scanner] Error 1
```

`internal/provider/codex/appserver/client.go`'s `readLoop` (line 90) reads newline-delimited
JSON-RPC frames from a live subprocess stream using `bufio.NewScanner(r)` with a manually
configured large buffer (`scanner.Buffer(make([]byte, 0, 64*1024), maxLineBytes)`,
`maxLineBytes = 64 * 1024 * 1024`) — a real, deliberate design choice to avoid the gate's stated
failure mode, but a **literal, mechanical violation of `check-no-scanner`'s "no raw
`bufio.NewScanner`" rule** all the same. The file was introduced by commit `65bcb7a`
("feat(codex): add app-server history backend with offline fallback", 2026-07-27T15:19:55Z):

```
$ git log --oneline -- internal/provider/codex/appserver/client.go
65bcb7a feat(codex): add app-server history backend with offline fallback
```

**This is the second known instance of the same gate-violation class, not the first — and it has
now survived four subsequent milestone landings unfixed:**

1. **First instance (found and properly fixed):** `internal/analyzer/tech_debt.go`'s
   `ScanSourceDir` used raw `bufio.NewScanner` to scan arbitrary source files (not JSONL) for
   TODO/FIXME/HACK/XXX markers. Found in session `a3ad0f35-2141-4f07-bada-5b7011b2acad` at
   2026-07-27T00:53:08Z ("Another pre-existing gate failure — raw `bufio.NewScanner` usage in
   `internal/analyzer/tech_debt.go`. Let me confirm this predates my changes before deciding what
   to do."), then an `AskUserQuestion` at 00:53:41Z presenting two options — "Skip pre-release
   checks (recommended)" vs. "Fix it properly first" — the human chose to fix it properly. The fix
   (commit `2c2c8cd`, "fix: replace raw bufio.Scanner with bufio.Reader in ScanSourceDir", landed
   2026-07-27T01:03:07Z) explicitly rejected `parser.ReadLineFiltered` (the gate's own suggested
   replacement) as **the wrong tool** for this call site: "`parser.ReadLineFiltered`... is designed
   for JSONL session parsing with base64 image-data stripping, which is the wrong tool here —
   applying its image/data-field filtering to arbitrary source code text could corrupt matches.
   Instead this follows the same `bufio.NewReader` + `ReadBytes('\n')` pattern already used by
   `internal/provider/claude/provider.go` and `internal/provider/codex/rollout.go`."

2. **Second instance (found, explicitly deferred, still unfixed today):**
   `internal/provider/codex/appserver/client.go:90`. During the DIR-030 adversarial-audit dispatch
   in session `b05a930b-8d45-42d8-98db-918c4fad6ade` at 2026-07-27T15:55:18Z, the audit prompt
   itself instructs the auditor to "Check the `check-no-scanner` pre-existing-failure claim: the
   build report says `make push`'s `check-no-scanner` flags
   `internal/provider/codex/appserver/client.go:90` and claims this predates DIR-030 (verified via
   `git stash`)... confirm this isn't something DIR-030 introduced or should have fixed." The audit
   accepted this as pre-existing and out of scope for DIR-030 — correctly, since `client.go` predates
   DIR-030's own landing commit (`450b14c`) — but no task was ever filed to actually fix it. It has
   since silently ridden through DIR-030 (`450b14c`), DIR-031 (`b293861`), DIR-032 (`2f93b73`), and
   the DIR-036 fix — four more landed milestones — still failing `make push`'s `lint`
   step, unnoticed because the routine dev loop (`make dev` → `make commit`) never runs `lint` at
   all; only `make push` does, and `make push` is the "before you push" step that appears to have
   been skipped or its failure tolerated across all of those landings.

**Root cause is structural, not a one-off typo, and mirrors the DIR-033 `FromSessionID` pattern
exactly**: the gate's own error message ("Use `parser.ReadLineFiltered` instead") is actively wrong
advice for at least two of its two known real violations — `ReadLineFiltered`
(`internal/parser/streaming_reader.go:27`) applies JSONL-specific base64-image stripping that is
inappropriate both for arbitrary source-code scanning (`tech_debt.go`'s case) and for a live
JSON-RPC subprocess stream (`client.go`'s case). Each time the gate has actually fired on a genuine
non-JSONL, line-length-sensitive read loop, a human/agent has had to hand-roll the same
`bufio.NewReader(r)` + `reader.ReadBytes('\n')` loop from scratch instead of reaching for a shared
helper — a repo-wide grep confirms this exact two-line shape is now independently duplicated in at
least four call sites with no shared abstraction:

```
$ grep -n "bufio.NewReader\|ReadBytes('\\\\n')" -r internal --include=*.go | grep -v _test.go
internal/provider/claude/provider.go:225:	reader := bufio.NewReader(f)
internal/provider/claude/provider.go:227:		line, err := reader.ReadBytes('\n')
internal/analyzer/tech_debt.go:166:		reader := bufio.NewReader(f)
internal/analyzer/tech_debt.go:169:			line, readErr := reader.ReadBytes('\n')
internal/mcp/query/stage.go:719:	r := bufio.NewReader(f)
internal/mcp/query/stage.go:722:		line, err := r.ReadBytes('\n')
internal/provider/codex/rollout.go:56:	reader := bufio.NewReader(f)
```

`client.go`'s `readLoop` needs the same treatment (or a shared helper) but has not received it —
there is no gate, lint rule, or CI check today that would have caught `client.go`'s violation before
merge (it apparently was tolerated/skipped at `65bcb7a`'s landing), and none that flags the four-way
duplicated hand-rolled replacement pattern either.

## Proposal

1. Fix `internal/provider/codex/appserver/client.go:90`'s `readLoop` to stop using raw
   `bufio.NewScanner`, following the same line-length-safe, non-JSONL pattern already established
   by `tech_debt.go`'s fix (`bufio.NewReader` + `ReadBytes('\n')`, preserving the existing
   `maxLineBytes` (64MB) cap behavior so a malformed/hostile peer still cannot grow memory
   unboundedly).
2. Crystallize the now four-times-duplicated `bufio.NewReader(f)` + `ReadBytes('\n')`-with-a-cap
   loop shape (`provider.go`, `tech_debt.go`, `stage.go`, `rollout.go`, and now `client.go`) into one
   shared helper in `internal/parser/` (a sibling to `ReadLineFiltered`, e.g.
   `ReadLineBounded(r *bufio.Reader, maxBytes int) ([]byte, error)`) that every non-JSONL,
   line-length-sensitive read loop can call instead of hand-rolling the loop again.
3. Fix `check-no-scanner`'s own error message (`Makefile:604`) so it no longer uniformly recommends
   `parser.ReadLineFiltered` — point instead at both legitimate replacements ("JSONL session
   content: `parser.ReadLineFiltered`; arbitrary line-length-safe reads: `parser.ReadLineBounded`")
   so the next violation's author isn't misdirected the way both prior fixes had to independently
   discover was wrong.
4. Migrate the pre-existing duplicated call sites (`provider.go`, `tech_debt.go`, `stage.go`,
   `rollout.go`) to the new shared helper as a mechanical follow-up (optional/best-effort — not
   required to close this task, but should not be left as a permanent architectural landmine
   without at least being tracked).
