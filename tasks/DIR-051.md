# `query_sessions(ancestors_of=...)` omits the `lineage_truncated` flag when traversal stops due to the `maxLineageDepth` bound, contradicting its own documented contract

## Finding

`handleAncestorsOf` (`internal/mcp/executor/query_sessions_handler.go:222-301`) walks a Codex thread's `ParentThreadID` chain upward. Its own doc comment (lines 214-221) and `docs/reference/codex-history-model.md:158-166` both state the same contract:

> "traversal stops (with a warning, never a silent truncation) on: a confirmed root, an explicit `unknown`, a project/cwd boundary crossing, a cycle, or the `maxLineageDepth` (32) bound"

and `docs/guides/mcp-query-tools.md:119` documents the caller-visible mechanism for this as the `lineage_truncated` flag: "Traversal stops — with a warning, never silently — at a confirmed root, an explicit `unknown`, a project/cwd boundary crossing, a cycle, or a depth limit."

The code sets a local `truncated` bool to `true` (which later causes `entries[len(entries)-1]["lineage_truncated"] = true` to be set, line 296-298) in exactly four of the five documented stopping conditions:

- cycle detected (line 258)
- ancestor lookup failure (line 266)
- project/cwd boundary crossing (line 271)
- explicit `LineageStatusUnknown` (lines 249, 279)

But **not** for the fifth: hitting `maxLineageDepth` (32) with a still-valid, still-in-boundary chain. That case falls through to the `for` loop's own exit condition (`i < maxLineageDepth` becoming false) without ever touching `truncated`. The post-loop check at line 288-290:

```go
if current != "" && !truncated {
    warnings = append(warnings, fmt.Sprintf("ancestor chain depth limit (%d) reached; traversal stopped", maxLineageDepth))
}
```

appends a human-readable warning string, but by this point `truncated` is still `false`, so the subsequent check at line 296:

```go
if truncated && len(entries) > 0 {
    entries[len(entries)-1].(map[string]interface{})["lineage_truncated"] = true
}
```

never fires. The result: a genuinely truncated (depth-bounded) ancestor chain is returned with a `warnings` array entry describing the truncation, but **no entry in the response ever carries `lineage_truncated: true`** — indistinguishable, from a caller that only inspects structured fields (not free-text warnings), from a complete chain that legitimately ended at a root.

Traced step by step for a chain of exactly 33+ valid, same-project ancestors with no cycle/unknown/boundary-crossing anywhere in the first 32 hops:
- Loop runs `i = 0..31` (32 iterations, bounded by `i < maxLineageDepth`).
- At the last iteration (`i == 31`), the 32nd ancestor is appended to `chain`, its lineage is `child` (not `unknown`), and `current = ancestor.ParentThreadID` is non-empty (a 33rd ancestor exists) — the `current == "" && i == maxLineageDepth-1` special case at line 282 does not fire since `current != ""`.
- Loop exits via the `for` condition (`i < maxLineageDepth` now false) — none of the `truncated = true` branches ran.
- Post-loop: `current != "" && !truncated` is true → the depth-limit warning is appended.
- `truncated` is still `false` → `lineage_truncated` is never added to any entry, even though the returned chain (32 entries) is objectively incomplete (a 33rd+ ancestor exists and was never returned).

This is untested: `query_sessions_handler_test.go`'s ancestor-related tests (`TestQuerySessions_AncestorsOf_KnownLineage`, `TestQuerySessions_AncestorsOf_UnknownLineageReportsUncertainty`, `TestQuerySessions_AncestorsOf_StopsAtProjectBoundary`, `TestQuerySessions_AncestorsOf_ClaudeProviderFailsClosed`) never construct a chain anywhere near 32 hops long, so the depth-bound code path (`i < maxLineageDepth` naturally exhausting) has no coverage at all.

## Proposal

Set `truncated = true` when the post-loop depth-limit warning fires, before (or as part of) appending it, e.g.:

```go
if current != "" && !truncated {
    warnings = append(warnings, fmt.Sprintf("ancestor chain depth limit (%d) reached; traversal stopped", maxLineageDepth))
    truncated = true
}
```

so the existing `if truncated && len(entries) > 0 { entries[...]["lineage_truncated"] = true }` block (already correct for the other four cases) also covers this one, matching the documented contract exactly.
