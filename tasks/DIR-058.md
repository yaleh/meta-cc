# ExtractToolCalls returns Go map-iteration order: analyze_bugs, get_work_patterns, and quality_scan retry_rate are nondeterministic on identical input

## Finding

`types.ExtractToolCalls` (`internal/types/toolcall.go:34-100`) pairs tool_use blocks
with their tool_result blocks correctly, but in Step 3 it emits the `[]ToolCall` slice
by iterating a **Go map**:

```go
// internal/types/toolcall.go:73
for toolUseID, tu := range toolUseMap {   // <- randomized iteration order
    ...
    toolCalls = append(toolCalls, tc)
}
```

Go randomizes map iteration order per range loop, so the returned slice order differs
on every call even for identical input. Every order-sensitive downstream consumer
therefore computes different numbers on every invocation of the same session data.

**Consumers that assume temporal order but do not sort:**

1. `internal/analyzer/bugs_analysis.go:40-50` — `AnalyzeBugs` scans `toolCalls` and,
   "for each error look ahead up to 3 positions for a fix" (`j := i + 1; j <= i+3`),
   i.e. positional adjacency in the shuffled slice.
2. `internal/analyzer/work_patterns.go:71-99` — `GetWorkPatterns` counts context
   switches between "consecutive tool calls" (`prevFile`/`prevTs` walking the slice
   in given order; the `if gap < 0 { gap = -gap }` at line ~90 papers over the fact
   that "consecutive" entries routinely have inverted timestamps).
3. `internal/analyzer/quality_analysis.go:46-65` — `QualityScan` retry detection:
   "a tool call with status error followed by the same tool within the next
   5 positions" — again positional adjacency in the shuffled slice.

Other consumers defensively sort (evidence the instability is known but handled
inconsistently): `internal/analyzer/sequences.go:28`,
`internal/query/sequences/sequences.go:61`, `internal/analyzer/edit_sequences.go:198`.
Neither `internal/analysis/service.go:148`/`:178` (the MCP analysis pipeline) nor the
three analyzers above re-sort.

**Live proof — identical fixed session, consecutive calls, different results**
(mined from session `16c504aa-6681-40b0-bfce-4f25f4dce679`, 2026-07-28; target
session `2a38491e-8724-4119-b3c7-6b12230216eb`, immutable historical data):

`analyze_bugs({scope:"project", session_id:"2a38491e-...", stats_only:true})`, run twice:

```
Run 1: {"patterns":[],"total_pairs":0,"data_source":"measured"}
Run 2: {"patterns":[
          {"error_signature":"0e79e4e2773267d3","fix_count":2,"recurrences":2,
           "examples":["unknown gate: vitest","unknown gate: vitest"]},
          {"error_signature":"d6e9126e6892fece","fix_count":1,"recurrences":1,
           "examples":["Exit code 1\n/usr/bin/python3: No module named pre_commit"]}],
        "total_pairs":3,"data_source":"measured"}
```

`get_work_patterns({scope:"project", session_id:"2a38491e-..."})`, run twice — all
fields byte-identical **except** the order-dependent one:

```
Run 1: "context_switches":6
Run 2: "context_switches":4
```

(Same 139 tool calls, same tool_frequency, same hourly_activity, same peak_hour;
only the adjacency-walk metric varies.)

**Recurrence / blast radius:** this fires on *every* call to `analyze_bugs`,
`get_work_patterns`, and `quality_scan` (retry dimension) — including this project's
own history-mining and self-validation routines, which use exactly these tools as
evidence sources. Defect patterns appear and disappear between runs (0 pairs vs 3
pairs above), so "recurring bug pattern" verdicts and any gate or task built on them
are not reproducible. `data_source:"measured"` advertises these numbers as measured
facts while they are partly random.

Not a duplicate: no task DIR-001..DIR-057 covers ExtractToolCalls ordering (grep of
`tasks/*.md` for determinism/ordering/map-iteration hits only DIR-001's SHA-dedup and
DIR-025's release-script determinism). DIR-050/053 (lifecycle turns dropped) and
DIR-028/036 (turn semantics) are about *which* records survive normalization, not the
*order* of paired ToolCalls.

## Proposal

1. Make `ExtractToolCalls` deterministic by emitting `ToolCall`s in input order:
   in Step 3, re-iterate `entries` (deterministic JSONL file order) and emit a
   `ToolCall` at each `tool_use` block, looking up its result in the already-built
   `toolResultMap`. Keeps the existing two-map pairing, removes the map-range emit.
2. Alternatively (or additionally) sort the result by parsed `Timestamp` with a
   stable tie-breaker (entry index / UUID). Either is acceptable; input-order
   iteration is the smaller change and matches what the defensive sorts in
   `sequences.go`/`edit_sequences.go` are approximating.
3. Add a regression test: build `[]SessionEntry` from ≥20 interleaved tool_use /
   tool_result blocks across ≥5 distinct tools with ≥2 errors, call
   `ExtractToolCalls` 50× in a loop, assert the emitted order (and the
   `AnalyzeBugs` `total_pairs` / `GetWorkPatterns` `ContextSwitches` /
   `QualityScan` retry count derived from it) is identical every iteration and
   matches the temporal expectation.
4. Optionally delete the now-redundant defensive sorts from step 2's consumers, or
   leave them as belt-and-braces — but document on `ExtractToolCalls` that the
   result is guaranteed in entry order.
