## Finding

`query_session_content` and `query_session_signals` declare `since`/`until` as global parameters, but they are only parsed and passed as `ParsedTimeRange` for role=user (`internal/mcp/handlers/handlers.go:30-39`), role=all (`handlers.go:219-228`), and type=timestamps (`handlers.go:285-297`). Every other path passes an empty `ParsedTimeRange{}`: role=assistant (`consolidated_handlers.go:54-74`), role=tool → `handleQueryToolBlocks` (`handlers.go:300-338`), type=errors (`handlers.go:190-201`), type=tokens (`handlers.go:203-213`), type=system_errors (`handlers.go:257-267`), type=tool_stats (`handlers.go:87-188`). Users pass `since`/`until` and get unfiltered results with no warning.

## Proposal

Wire `since`/`until` parsing into ALL handler paths and pass the resulting `ParsedTimeRange` through to the query layer. Where a path genuinely cannot support time filtering (no timestamp on the record shape), return a clear validation error naming the unsupported combination instead of silently ignoring the parameters. Prefer implementation over erroring wherever the record shape carries a timestamp.

## Plan

1. Extract the existing since/until parse logic into a shared helper.
2. Apply it in every handler path listed above; thread `ParsedTimeRange` into each query call.
3. Add per-path tests: time-filtered queries on role=assistant, role=tool, type=errors, type=tokens, type=system_errors, type=tool_stats return only in-range records.
4. Update tool parameter docs if any path legitimately rejects the combination.
