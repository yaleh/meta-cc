## Finding

meta-cc currently publishes mutually inconsistent capability metadata:

- `.claude-plugin/marketplace.json` reports version `3.4.0` and advertises 22 MCP tools.
- `plugin-src/.codex-plugin/plugin.json` reports version `3.0.7`.
- the MCP startup banner reports server version `1.0.0`.
- the live `tools/list` response and server tests expose 15 tools.
- `CLAUDE.md` and several project documents still advertise 21 tools, while the public README uses 15.

This is not merely cosmetic. Agents use the tool count to decide whether capabilities are missing, package managers use versions to decide whether an update is available, and release verification cannot distinguish a correctly assembled bundle from a stale one.

## Proposal

Create one machine-readable release/capability source of truth and generate or verify every published version and tool-count surface from it.

### Contract

- The server version, Claude marketplace version, Codex plugin version, release archive metadata, and documentation release version must agree.
- The advertised MCP tool count must be derived from the actual registered tool definitions, not maintained as an independent magic number.
- CI and local release checks must fail with a useful diff when a version or tool-count surface drifts.
- Historical proposal/plan statements may remain as historical records, but current guides, manifests, banners, and examples must be corrected.

### Design constraints

Prefer a small checked-in metadata file plus a deterministic verification/generation script over parsing prose. Avoid silently rewriting manifests during ordinary builds. The check must run without network access and must distinguish current product documentation from historical design documents. Do not change the tool set solely to make an old count true.

### Alternatives considered

- Manually editing all numbers fixes today's snapshot but guarantees recurrence.
- Treating each package format as independently versioned is unsupported by the current release process and confuses users.
- Counting documentation occurrences with a broad grep would incorrectly flag historical documents.

## Plan

1. Inventory all current version and tool-count surfaces, categorize them as authoritative, generated/verified, historical, or test fixtures, and add failing consistency tests.
2. Introduce the smallest machine-readable release metadata source and a script or Go helper that compares it with plugin manifests, the compiled server version, and the actual `GetToolDefinitions()` count.
3. Wire the consistency check into `make check-release-ready`, plugin-sync checks, and CI without requiring network access.
4. Correct current manifests, startup/version output, README/CLAUDE guidance, installation docs, and MCP reference pages. Clearly mark historical counts where needed rather than rewriting history.
5. Add a contributor/release note explaining how a version bump and tool addition are performed and verified.
6. Run the focused consistency checks, package tests, release smoke checks, and repository commit gate.

## Acceptance Criteria

- [ ] One documented machine-readable source defines the current release version.
- [ ] Every shipped Claude/Codex/server version surface agrees with that source.
- [ ] The current advertised tool count equals the real `tools/list` count.
- [ ] A deliberately stale manifest or current-doc count makes the consistency test fail with an actionable message.
- [ ] Historical proposal and plan records are not treated as current product claims.

## Definition of Done

- [ ] Offline consistency verification is part of normal pre-release CI.
- [ ] Current user-facing documentation contains no contradictory version or tool-count claims.
- [ ] `make commit` passes.
