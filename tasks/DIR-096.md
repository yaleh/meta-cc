## Finding

During the 2026-07-30 dogfooding analysis session, `analyze_bugs` with `limit: 3` (examples per pattern) still produced 92KB (75 patterns) and was forced to file_ref mode. The `examples` entries are bare strings with no session/timestamp structure, and a consumer parsing them as objects hit AttributeError.

DIR-004's own finding noted analysis tools bypass the query pipeline entirely; DIR-019 (done) fixed total-error tracking but not output shape or pattern count. Today, even a modest per-pattern `limit` cannot prevent output blowup, because the pattern count itself is unbounded and defaults to everything (75 patterns on this project's 5-day corpus).

Compounding evidence from the same session: `query_sessions` hard-failed with `MCP error -32603: provider claude: no Claude entries in /home/yale/.claude/projects/-home-yale-work-meta-cc/8eda8f4e-2c74-4176-ba6b-8c45e890df42.jsonl` (tolerance tracked in DIR-094; time-window support for `analyze_bugs` tracked in DIR-095).

## Dependencies

Follows DIR-004 (done, pagination/file_ref) and DIR-019 (done, total-error tracking). Not a duplicate: this extends their contract to the bug-pattern analyzer's output shape and pattern count, which neither addressed.

## Evidence

Implemented on `task/DIR-096` (commit `eef3f56 feat(analysis): cap analyze_bugs patterns and structure its examples`), confined to the declared `## Touches` paths.

**What changed** (`internal/analysis/service.go`, plus the schema in `internal/mcp/tools/tools.go`; the `internal/mcp/executor` handler needed no change — it passes args straight through):

- `max_patterns` (default 20, `0` = unlimited), counted after a **total** ordering (recurrences desc, fix_count desc, signature asc). The analyzer built its slice by ranging a map and sorted by recurrences only, so ties previously left "which N survive the cap" to Go's map iteration order; `TestService_AnalyzeBugs_DefaultIsDeterministic` pins the cap to the same patterns run-to-run.
- `examples` promoted from bare error strings to `{session_id, timestamp, error_text, fix_text?, signature}`. `session_id` is resolved **positionally** against `types.ExtractToolCalls`' emit order, not by UUID — the provider normalization path (`internal/provider/records/records.go`) emits `sessionId` with no `uuid`, so a UUID-keyed lookup silently attributed nothing on that path.
- Size is bounded structurally, not by corpus luck: `error_text`/`fix_text` clipped at 500 bytes on a rune boundary, and the examples section as a whole capped at a 16KB budget, so one oversized message (largest observed: 10,148 chars) cannot crowd out every other pattern.
- `stats_only` still short-circuits before any example collection.
