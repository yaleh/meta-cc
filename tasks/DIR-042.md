## Finding

`docs/guides/mcp-query-tools.md:382` documents `stats_only` as: `| stats_only | boolean | Return
aggregate statistics only |`, and every one of the six `analysis.Service`-backed MCP tools
(`analyze_bugs`, `analyze_errors`, `quality_scan`, `get_work_patterns`, `get_timeline`,
`get_tech_debt`) advertises `stats_only` in its MCP tool parameter schema. CLAUDE.md's own FAQ
tells users to rely on `stats_only`/`stats_first` specifically to keep result size small:
"Use consolidated query tools for common questions... `query_session_signals({type: 'tokens',
stats_first: true})`" and "the system automatically switches to file_ref mode for large result
sets" — the documented mental model is that `stats_only` reliably shrinks output to a small
aggregate.

In `internal/analysis/service.go`, only **one** of these six methods actually implements this
contract:

```
$ grep -n "boolArg(args, \"stats_only\")\|func (s \*Service)" internal/analysis/service.go
229:func (s *Service) AnalyzeBugs(args map[string]interface{}) (string, error) {
242:func (s *Service) AnalyzeErrors(args map[string]interface{}) (string, error) {
255:func (s *Service) QualityScan(args map[string]interface{}) (string, error) {
268:func (s *Service) GetWorkPatterns(args map[string]interface{}) (string, error) {
289:func (s *Service) GetTimeline(args map[string]interface{}) (string, error) {
305:	if boolArg(args, "stats_only") {
394:func (s *Service) GetTechDebt(args map[string]interface{}) (string, error) {
```

`boolArg(args, "stats_only")` is referenced exactly once in the entire file, inside `GetTimeline`
(line 305), which correctly short-circuits to a small `analyzer.GetTimelineStats(entries)` summary
when `stats_only` is set. `AnalyzeBugs` (229), `AnalyzeErrors` (242), `QualityScan` (255),
`GetWorkPatterns` (268), and `GetTechDebt` (394) never read `args["stats_only"]` at all — each
simply calls its underlying analyzer with the full entry/toolCall set and marshals the complete
result, regardless of what the caller passed for `stats_only`. The only knob any of these five
respect is `limit` (`intArg(args, "limit")`), whose own schema description says "Max examples per
group (0 = unlimited)" — i.e. even that knob defaults to unbounded.

**Reproduced live in this exact session, causing an actual tool failure**: calling
`analyze_errors({stats_only: true})` (default provider/scope, no `limit` override) against this
project's own history returned a result **74,059 characters** long — so far past the tool-output
token budget that the call itself errored: `"Error: result (74,059 characters across 1 line)
exceeds maximum allowed tokens."` Inspecting the saved output confirms why: with `stats_only: true`
the response still included a full, untruncated `by_tool[].examples` array per tool — e.g. the
`Bash` group alone carried 21 example strings (one **3,988 characters** long) — i.e. `stats_only`
produced the *same shape* of output as the non-stats-only call (`total_errors`, `by_tool` with
per-entry `examples`, `by_type` with per-entry `examples`), not an aggregate summary. This directly
contradicts both the tool's own documented contract ("Return aggregate statistics only") and
`GetTimeline`'s own sibling implementation in the same file, which demonstrates what honoring
`stats_only` is supposed to look like.

## Proposal

1. For each of `AnalyzeBugs`, `AnalyzeErrors`, `QualityScan`, `GetWorkPatterns`, and `GetTechDebt`,
   add the same `if boolArg(args, "stats_only") { ... }` short-circuit `GetTimeline` already has,
   returning a genuinely aggregate-only summary (counts per tool/type/pattern, no per-item
   `examples`/details arrays) — introducing a small `*Stats` result type per analyzer where one
   does not already exist, following `analyzer.GetTimelineStats`'s existing shape as the template.
2. Where `stats_first` is also documented/schema'd for these tools, apply the same fix so it
   actually returns a stats summary followed by details, rather than only the full details.
3. Regardless of the fix, cap `examples` arrays to a small bounded default (e.g. reuse the existing
   `limit` semantics but do not allow `limit=0` to mean "put literally every full-text example,
   unbounded in string length, into every response") so a single large error/example string cannot
   alone blow the response past the hybrid inline/file_ref threshold or the model's token budget.

## Acceptance Criteria

- [ ] `analyze_errors({stats_only: true})` against this project's own session history returns a
      result with no `examples` field (or an empty/tightly-bounded one) under a small size ceiling
      (e.g. under the 32KB `inline_threshold_bytes` default) — verified by an actual run, not
      narrative claim, and specifically must not reproduce today's 74,059-character/token-limit
      failure.

      per method), not one.
