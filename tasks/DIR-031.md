## Finding

Codex project queries currently load and parse all matching rollout files before applying content filters. This is acceptable for the present small corpus but scales poorly to hundreds of sessions and multi-gigabyte rollouts. `history.jsonl` provides a lightweight prompt index but is optional and incomplete, while app-server title search does not replace full message/tool search.

## Dependencies

Depends on DIR-028 for a stable canonical item model and DIR-030 for precise session discovery and filtering.

## Proposal

Add an optional local SQLite FTS5 index over normalized conversation items. Indexing is incremental, local-only, recoverable, and backend-neutral. Raw session stores remain authoritative; the index is a derived cache that can be rebuilt or bypassed.

## Contract

- Index identity includes provider, thread ID, turn ID, item ID, role/type, cwd, timestamps, title, tool name, and searchable text.
- Invalidation uses authoritative updated metadata plus rollout path, size, mtime, and backend/schema version where available.
- Interrupted indexing is transactional and never exposes partially replaced session data.
- Deleted, archived, moved, and rewritten sessions are reconciled.
- Search returns provenance and can hydrate exact canonical records after candidate selection.
- Tool outputs are size-limited and excluded or redacted by default; secrets are not intentionally indexed.
- Users can disable, inspect, rebuild, and clean the derived index.

## Plan

1. Define the index schema, privacy policy, versioning, and migration strategy.
2. Implement per-session transactional upsert and stale-session reconciliation.
3. Add FTS query planning with metadata filters and exact-record hydration.
4. Use `history.jsonl` only as an optional discovery accelerator, never as the sole source of truth.
5. Add benchmarks for cold indexing, incremental refresh, and representative searches.
6. Add corruption recovery and explicit rebuild/cleanup operations.

## Acceptance Criteria

- [ ] An unchanged corpus performs no deep reparse on incremental refresh.
- [ ] Modifying one session reindexes only that session.
- [ ] Search results match a direct canonical scan on test corpora.
- [ ] Archive/delete/move operations remove or update stale index rows.
- [ ] Index corruption degrades to rebuild or direct query without losing source history.
- [ ] Privacy defaults exclude oversized tool output and documented sensitive fields.

## Definition of Done

- [ ] Functional, migration, recovery, and benchmark tests pass.
- [ ] Index location, lifecycle, privacy, and cleanup are documented.
- [ ] `make commit` passes.

## Continuation finding (2026-07-29)

The FTS5 package landed in commit `b293861`, but the original user-facing performance finding remains open. Repository-wide call-site inspection finds `internal/ftsindex` referenced only by its own package tests; `query_session_content`, `query_session_signals`, and the provider record pipeline never open, refresh, search, or hydrate from the index. `internal/provider/records.Build` still lists every matching session and calls `LoadTurns` before applying content filters.

This task is reopened because its original Contract requires indexed search with exact-record hydration, and its Finding specifically targets project-query full parsing. The remaining implementation must wire the derived index into the actual MCP content-search path, retain a direct-scan fallback, expose bounded warnings/rebuild behavior, and prove result parity against direct canonical scans.

Additional acceptance evidence required:

- A project content query over multiple unchanged sessions uses the FTS candidate path and does not call `LoadTurns` for every session.
- Candidate hits are hydrated back to canonical records before response filtering and formatting.
- Unsupported query shapes, disabled/degraded FTS5, stale/corrupt indexes, and exact `session_id` queries fall back without false negatives.
- End-to-end MCP tests demonstrate parity with direct scan for provider, role, pattern/contains, time, context, grouping, pagination, and jq post-filter composition.
