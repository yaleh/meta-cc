## Finding

The provider-aware convenience query path can search Codex sessions, but the two stage-1 discovery tools are still Claude-only. A live call to `get_session_directory({"provider":"codex"})` returned a path under `~/.claude/projects`, and `get_session_metadata({"provider":"codex"})` returned Claude file paths and a Claude-specific JSONL schema. Their schemas in `internal/mcp/tools/tools.go` do not declare `provider` or `working_dir`, and `internal/mcp/query/stage.go` routes directly through `SessionLocator`.

This breaks a basic invariant: once a caller selects a provider, discovery, metadata, and subsequent queries must describe the same corpus. It can also lead an agent to inspect the wrong files while believing it is observing Codex.

## Proposal

Make `get_session_directory` and `get_session_metadata` provider-aware through the same locator/provider abstractions used by the convenience query tools.

### Contract

- Add `provider` (`claude` default, `codex`, or `all`) and `working_dir` to both MCP tool schemas.
- `provider=claude` must retain the existing response shape and behavior.
- `provider=codex` must resolve only Codex rollout files for the requested project/session and return Codex-appropriate file paths and schema hints.
- `provider=all` must return an explicit per-provider representation; it must not pretend that Claude and Codex files share one directory or one raw schema.
- Invalid/unavailable providers and an unsupported provider/scope combination must fail with an actionable error instead of silently falling back to Claude.

### Design constraints

Do not duplicate Codex SQLite or rollout discovery in the stage handlers. Extract or reuse a provider-aware file-selection service shared with the existing query pipeline. Preserve streaming behavior and never read production rollout files wholesale merely to compute metadata. Include the selected provider in the response so downstream agents can verify provenance.

### Alternatives considered

- Removing `provider` from these tools would leave the advertised two-stage workflow incomplete for Codex.
- Returning the common normalized schema would be misleading because these tools expose raw files for stage-2 jq queries.
- Silently mapping `all` to one provider would hide data loss.

## Plan

1. Add failing schema and handler tests covering `provider=claude`, `provider=codex`, `provider=all`, `working_dir`, invalid providers, missing Codex state, and provider/scope edge cases. Use temporary Claude and Codex homes; never depend on the developer's real session history.
2. Refactor provider-aware raw-file selection out of the existing query path into a reusable unit. Update `internal/mcp/query/stage.go` to consume it for both discovery tools.
3. Define provider-specific raw schema metadata and an unambiguous multi-provider response. Keep the existing Claude-only response backward compatible.
4. Update `internal/mcp/tools/tools.go`, MCP reference docs, examples, and Codex E2E coverage so advertised parameters and live behavior agree.
5. Run focused package tests, `make test-e2e-codex`, and the repository commit gate.

## Acceptance Criteria

- [ ] A synthetic Codex project returns only Codex rollout paths from both discovery tools.
- [ ] Claude-default calls remain backward compatible.
- [ ] `provider=all` preserves provider provenance and raw-schema differences.
- [ ] Unsupported combinations fail closed with actionable errors.
- [ ] MCP schemas, reference docs, unit tests, and E2E tests describe the same contract.

## Definition of Done

- [ ] New and changed Go code has focused tests with at least 80% package coverage.
- [ ] `make test-e2e-codex` passes.
- [ ] `make commit` passes.
