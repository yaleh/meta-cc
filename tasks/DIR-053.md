# `providerrecords.Normalize` still drops lifecycle-only Codex turns even after DIR-050's `flush()` fix, so MCP callers still never see them

## Finding

DIR-050 (commit `c372d4a`) fixed `internal/provider/codex/rollout.go`'s `turnBuilder.flush()` so a
Codex rollout turn whose only content is a typed lifecycle item (`session_end`, `turn_aborted`,
`compaction`) is now retained in the `[]conversation.Turn` slice returned by `loadTurnsFromRollout`,
instead of being silently discarded.

DIR-050's adversarial audit (fresh-context, independently reproduced via a downstream-consumer
search) found that this fix does not fully close the loop the task's own Finding section used to
justify itself. The Finding explicitly motivated the fix by saying "the session looks like it has no
history at all to any MCP caller (`query_session_content`, analysis tools, `query_sessions`'s
turn-derived fields)" — but `internal/provider/records/records.go`'s `Normalize` function (the only
place downstream of `loadTurnsFromRollout` that turns `conversation.Turn` structs into the
query-time records MCP tools actually operate on) reads only `Turn.UserText`/`AssistantText`/
`ToolCalls`/`TokenUsage` — it never reads `Turn.Items` or `Turn.Status` at all.

Concretely: a lifecycle-only turn (post-DIR-050) now exists in the raw `[]conversation.Turn` slice
with `UserText == ""`, `AssistantText == ""`, `ToolCalls == nil`, but `Items` containing the typed
`ItemKindSessionEnd`/`ItemKindCompaction` entry and/or `Status == TurnStatusAborted` set.
`Normalize`'s existing per-field emission logic (each of which is presumably still gated on the
corresponding field being non-empty, following the same pattern as the pre-fix code) will therefore
still emit **zero** records for this turn — the typed lifecycle item, though now retained in the raw
Turn slice, remains invisible to every MCP tool (`query_session_content`, `query_session_signals`,
analysis tools, `query_sessions`'s turn-derived fields), because none of them go through anything
other than `Normalize`'s narrow projection.

In other words: DIR-050 fixed the *low-level* Codex rollout parser (`loadTurnsFromRollout`) to retain
these turns, but the *next layer up* (`providerrecords.Normalize`) still silently drops them on the
floor before they ever reach a caller — the exact "session looks like it has no history" symptom the
DIR-050 Finding described is still reproducible end-to-end via any actual MCP tool call, even though
the raw Go-level Turn slice is now correct.

This is not a criticism of DIR-050's build (its AC/DoD were correctly scoped only to
`loadTurnsFromRollout`/`flush()` and did not mention `records.Normalize` or MCP tools at all — DIR-050
is fully done per its own literal contract) — this is a distinct, additional gap one layer up that
needs its own task.

## Proposal

1. Extend `providerrecords.Normalize` (`internal/provider/records/records.go`) to also emit a record
   for a turn whose `Items` contains an `ItemKindSessionEnd`/`ItemKindCompaction` entry, or whose
   `Status` is non-default (e.g. `TurnStatusAborted`), even when `UserText`/`AssistantText`/
   `ToolCalls` are all empty — mirroring the same widening DIR-050 applied to `flush()`'s retention
   condition, but at the normalized-record layer.
2. Decide what such a record should look like (e.g. a minimal record carrying just `type`,
   `turn_status`, and/or the lifecycle item's fields) and confirm at least one MCP tool
   (`query_session_content` with `role=all`, or `query_sessions`'s turn-derived status field) can
   actually observe it end-to-end via a live/simulated tool call.
3. Add a regression test at the `providerrecords`/MCP-handler layer (not just the
   `internal/provider/codex` layer DIR-050 already covers) proving a lifecycle-only turn survives all
   the way through to an actual MCP tool response.
