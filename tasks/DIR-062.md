# query_session_content `contains` is a silent no-op for role=user/tool/all

## Finding

The `query_session_content` tool schema advertises `contains` as a general, cross-role substring filter, but the implementation only honors it when `role=assistant`. For `role=user`, `role=tool`, and `role=all`, the parameter is accepted and then silently dropped — the query returns **unfiltered** results with no warning. A caller who believes they filtered gets a full result set back.

Evidence — schema vs implementation:

- Schema, `internal/mcp/tools/tools.go:405-408`:
  ```go
  "contains": {
      Type:        "string",
      Description: "Optional literal substring filter applied to message content (case-insensitive). ... When role=assistant, use '## Summary' to retrieve summaries.",
  },
  ```
  The description never restricts `contains` to `role=assistant`; the assistant mention is only a usage hint. Contrast `pattern` (tools.go:409-412), which IS explicitly documented "(only applies when role=user)".

- Implementation, `internal/mcp/executor/consolidated_handlers.go`:
  - `role=assistant` branch (lines 52, 60-76) reads `contains` and injects a jq `test()` filter. ✅
  - `role=user` branch (lines 40-48) only reads `pattern`/`content_type`; `contains` is never read. ❌
  - `role=tool` branch (line 79-81) delegates to `handleQueryToolBlocks`.
  - `handleQueryToolBlocks` (`internal/mcp/executor/handlers.go:269-294`) reads provider/block_type/tool_name/limit/working_dir/include_subagents/session_id — **never `contains`**. ❌
  - `role=all` branch (lines 83-85) delegates to `handleQueryConversationFlow`, which also does not read `contains`. ❌

Evidence — live reproduction (this project's own MCP server, session 16c504aa-6681-40b0-bfce-4f25f4dce679):

A query with a string guaranteed to match nothing still returns records:
```
query_session_content({role:"tool", block_type:"tool_result",
                       contains:"ZZZ_SHOULD_MATCH_NOTHING_999", limit:5})
→ returned_records: 5   (turns 0-4 of the current session; none contain the string)

query_session_content({role:"user",
                       contains:"ZZZ_SHOULD_MATCH_NOTHING_999", limit:5})
→ returned_records: 5   (user turns 0-4; none contain the string)
```
A working filter would return 0 records. Both returned 5, proving `contains` is ignored for these roles.

Recurrence pattern: this is the same failure class as the dead-schema-parameter findings (DIR-041/042/043/044/048), but nastier — those params were dead everywhere and got a static gate (DIR-045). `contains` works for ONE role and silently lies for the others, so a dead-param allowlist gate cannot catch it: the parameter is "used" (in the assistant branch) and passes any presence check. CLAUDE.md's own guidance ("Query messages/content → query_session_content(role=user|assistant|tool|all)") invites exactly the cross-role `contains` usage that silently fails.

This is distinct from DIR-047 (regex-injection in the assistant `contains` branch, fixed) and from the dead-param DIRs (params dead across all roles).

## Proposal

Pick one and make the behavior match the schema:

1. **Honor `contains` cross-role (preferred)** — in `handleQuerySessionContent`, apply the same `regexp.QuoteMeta` + `EscapeJQ` + jq `test(...; "i")` filter for `role=user` (on `.message.content`), `role=tool` (on the block's `.content`/`.text`), and `role=all`. Reuse one helper so the escaping is identical to the assistant branch (avoid a second DIR-047-style divergence).
2. **Fail loudly** — if `contains != ""` and `role != "assistant"`, return an error (or append a `warnings[]` entry) stating `contains` only applies to role=assistant, and tighten the schema description to say so explicitly (mirror the `pattern` "(only applies when role=user)" wording).

Either way, add a regression test that a never-matching `contains` returns 0 records for role=user and role=tool.
