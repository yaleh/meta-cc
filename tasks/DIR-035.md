## Finding

The exact same infrastructure defect — the process environment that invokes `make commit`/`make`-based gates does not have `/usr/local/go/bin` (where `go` and `gofmt` actually live: `which go` → `/usr/local/go/bin/go`) on `PATH`, causing `go: command not found` (exit 127) or a spurious gate FAIL — has recurred at least **six** separately-evidenced times across this repo's own Claude Code session history, and was already known and manually worked around once, ~20 tasks ago, before the workaround was silently dropped:

1. **Raw `go: command not found` (exit 127) tool errors, 8 occurrences across 2 sessions**, each inside a dispatched build subagent (`isSidechain: true`, distinct `agentId`s):
   - Session `2a38491e-8724-4119-b3c7-6b12230216eb`, 2026-07-25T16:27:25Z, 16:34:38Z, 16:34:39Z, 16:36:32Z (4 occurrences, agentIds `a2adaa1c33762b335`, `a4bfbb874675fb340`, `accd3f1c38e10f5c0`).
   - Session `eb482896-9962-4f8e-8fc0-8b63100bbaf6`, 2026-07-26T01:15:19Z, 01:24:07Z, 01:30:57Z, 01:34:03Z (4 occurrences, agentIds `a3c8d9c3a74cd7d3f`, `a5b142f70e0a940b4`, `a22601ecb907a37ac`, `a3380b9b6153c6114`).
2. **`tasks/DIR-024.md`'s own needs-human note** (line 68): "the `gate_run` MCP tool itself misreports FAIL here because its subprocess doesn't inherit `/usr/local/go/bin` from `~/.bashrc` — an environment quirk unrelated to this task, verified separately by running `make commit` directly with `PATH` corrected."
3. **`tasks/DIR-025.md`'s own needs-human note** (line 74): "this environment's `gate_run` MCP tool subprocess doesn't inherit `/usr/local/go/bin` from `~/.bashrc`, a known unrelated infra quirk — see DIR-024's notes."
4. **`tasks/DIR-027.md`'s own needs-human note** (lines 66-79): the automated `acceptance` gate failed **twice in a row with exit 2** on a fully-passing diff; root cause confirmed by the auditor running a plain `bash -c 'echo $PATH'` in the workspace and finding no `/usr/local/go/bin`; manually running `PATH="/usr/local/go/bin:$PATH" make commit` in the identical worktree/diff passed cleanly. The note explicitly predicts: "every future `acceptance` gate run for any Go-based task in this repo will spuriously FAIL the same way until the gate runner's PATH is fixed."
5. A related symptom of the same PATH-fragility class: **`goimports not installed or available in the PATH`** during a pre-commit hook run (session `a3ad0f35-2141-4f07-bada-5b7011b2acad`, 2026-07-26T16:20:18Z, `Exit code 143` after a 3-minute timeout), and `ls: cannot access '/home/yale/go/bin': No such file or directory` (same session, 2026-07-26T16:20:47Z) — both PATH/toolchain-location assumptions breaking in the same class of minimal-environment subprocess.
6. **The fix was already known and applied once, then lost.** `tasks/DIR-005.md`, `tasks/DIR-006.md`, and `tasks/DIR-007.md` (much earlier tasks) all set `extra.acceptance` to a value that begins `export PATH=/usr/local/go/bin:$PATH && cd ...` — i.e. an earlier task author already hand-rolled the exact workaround. But every task from `DIR-024` onward (`DIR-024` through `DIR-034`, verified via `grep -n "acceptance:" tasks/DIR-0{24..34}.md`) uses the bare `acceptance: make commit`, with no PATH prefix — the convention was not propagated or centralized, so the same class of failure had to be independently rediscovered and manually worked around by a human/auditor at least 3 more times (DIR-024, DIR-025, DIR-027).

Root cause is structural: the fix (prefixing `PATH=/usr/local/go/bin:$PATH`) was pushed down into **individual task files' `extra.acceptance` strings** instead of being centralized once in the thing that's actually PATH-fragile — `Makefile` itself (or a single wrapper all gates route through). Every task author has to remember to re-add the workaround, and most don't, because there is no gate or lint check that would catch a task's `acceptance` field silently regressing to a bare `make commit`.

## Proposal

Centralize the PATH fix in the `Makefile` itself so gate/build correctness no longer depends on the invoking process's inherited `PATH`, and stop requiring every task's `extra.acceptance` field to re-derive the same workaround:

1. Add a `PATH` hardening line near the top of `Makefile` (e.g. `export PATH := $(PATH):/usr/local/go/bin:$(HOME)/go/bin`) so every recipe's shell invocation — regardless of what launched `make` — can find `go`, `gofmt`, and `goimports` (once installed to `$(HOME)/go/bin` via `go install`).
2. Verify `$(GOCMD)`-based targets (`build`, `test`, `dev`, `commit`, `push`, `lint`) succeed when invoked with a deliberately minimal `PATH` (e.g. `env -i PATH=/usr/bin:/bin make commit` or equivalent), reproducing the exact failure mode documented above and proving the fix closes it.
3. Simplify `tasks/DIR-005.md`, `tasks/DIR-006.md`, `tasks/DIR-007.md`'s `extra.acceptance` fields back to a bare `make commit`/equivalent now that the workaround lives centrally (optional cleanup, not required for the fix itself — do not treat as blocking).
4. Document the fix and its rationale (a one-line comment above the `export PATH` line in the `Makefile`, citing this task) so a future contributor does not strip it as dead code.

## Contract

- `make commit`, `make dev`, `make push`, and `make test` succeed when invoked by a subprocess whose inherited `PATH` lacks `/usr/local/go/bin` and `$(HOME)/go/bin`, as long as `go` is actually installed at one of those conventional locations.
- No change to `Makefile` target *behavior* for a normal, already-correct developer shell — the fix only adds fallback directories, it does not reorder or remove any existing `PATH` entries a developer relies on.
- The fix is exercised by an automated check (not just narrative claims) that fails if the PATH hardening is later removed.

## Plan

1. Reproduce the failure directly: run `env -i HOME="$HOME" PATH=/usr/bin:/bin make -C /home/yale/work/meta-cc commit` (or a narrower single target) in a scratch worktree and confirm it fails with `go: command not found`, matching the cited session evidence.
2. Add the `export PATH := $(PATH):/usr/local/go/bin:$(HOME)/go/bin` (or equivalent, adjusted for actual `GOROOT`/`GOBIN` conventions) line near the top of `Makefile`.
3. Re-run the same minimal-`PATH` repro command and confirm it now succeeds (or fails only for genuine code/test reasons, not `command not found`).
4. Add this repro as a lightweight regression check invokable from `make commit` or `make push` (e.g. a `check-path-independence` target that runs a trivial `go version`-style command inside a `PATH`-stripped subshell as part of the check suite) so silent regression is caught automatically rather than requiring another manual audit note.
5. Run the full `make commit` / `make push` suite normally (with an unmodified developer `PATH`) to confirm no regression for the common case.
