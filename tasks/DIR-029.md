## Finding

meta-cc currently treats Codex's private SQLite and rollout formats as its primary history API. OpenAI documents `codex app-server` as the integration surface for conversation history and explicitly states that transcript format is not a stable interface. Codex 0.145 exposes stable `thread/list` and `thread/read(includeTurns=true)` methods, while raw history is evolving toward paginated/projection-backed storage.

A live audit also showed important default-filter behavior: an unqualified `thread/list` returned only a subset of project sessions. `modelProviders: []`, explicit `sourceKinds`, archived handling, and `useStateDbOnly` semantics must be controlled deliberately.

## Dependency

Depends on DIR-028 because app-server returns ordered turns and items that should map into the canonical model without flattening.

## Proposal

Introduce a Codex history backend abstraction with `auto`, `app_server`, and `files` modes. In `auto`, negotiate with the installed Codex app-server using its initialization handshake and stable read methods, then fall back to the existing SQLite/rollout backend on absence, timeout, incompatible schema, or process failure. Raw-file support remains first-class for offline and forensic use.

## Contract

- Only read-only stable methods `thread/list` and `thread/read` are required in the first release.
- App-server startup has bounded timeouts, cancellation, stderr isolation, process cleanup, and a circuit breaker for repeated failures.
- Listing explicitly defines provider, source-kind, cwd, archived, pagination, and sorting behavior; defaults must never silently omit eligible sessions.
- App-server failures fall back in `auto` mode with structured warnings and provenance.
- `app_server` mode fails clearly instead of silently using files.
- No query resumes, mutates, archives, repairs, or deletes a Codex thread.
- Tests use isolated `CODEX_HOME` directories and never read or modify the developer's real history.

## Plan

1. Define the backend interface and configuration resolution.
2. Implement the app-server JSONL client, initialization handshake, request correlation, pagination, timeout, and shutdown.
3. Map `thread/list` and `thread/read` responses into the canonical conversation model.
4. Implement `auto` fallback and backend provenance/warning reporting.
5. Add a fake app-server test harness plus a version-gated isolated E2E test against the installed Codex CLI.
6. Document supported stable methods and explicitly exclude experimental history APIs from the initial contract.

## Acceptance Criteria

- [ ] App-server mode lists and reads synthetic threads without mutation.
- [ ] Explicit filters return interactive, exec, alternate-provider, archived, and subagent sessions when requested.
- [ ] Auto mode falls back after bounded failure and reports which backend supplied results.
- [ ] File mode continues to work when the Codex executable is absent.
- [ ] No child app-server process survives server shutdown or request cancellation.

## Definition of Done

- [ ] Configuration and operational diagnostics are documented.
- [ ] `make commit` passes.

## needs-human: adversarial audit REFUTATION FOUND (2026-07-27, loop-driver)

Build (worktree `/home/yale/work/meta-cc-worktrees/DIR-029`, branch
`milestones/meta-cc/DIR-029`, uncommitted) passed the `acceptance` gate
(`make commit` green), but the fresh-context adversarial auditor found a real,
reproduced defect that makes real-subprocess `app_server` mode non-functional:

**Root cause** — `connectProcess` in `internal/provider/codex/appserver_provider.go`
(~lines 60-83) does:
```go
return func(ctx context.Context) (threadSource, io.Closer, error) {
    ctx, cancel := context.WithTimeout(ctx, startupTimeout)
    defer cancel()          // fires when this closure returns
    ...
    proc, err := appserver.StartProcess(ctx, ...)   // uses exec.CommandContext(ctx, ...)
    ...
    return proc.Client, proc, nil   // defer cancel() runs immediately after this
}
```
`exec.CommandContext`'s internal watcher goroutine kills the process the moment
`ctx.Done()` fires — regardless of whether `Wait()` has completed. Since `cancel()`
is deferred *inside this connector closure*, it fires as soon as `connect()`
returns (right after a successful `Initialize()` handshake), long before
`listSessions`/`getSession` get to call `ThreadList`/`ThreadRead` on the same
process, and long before the separately-deferred `closer.Close()` ever runs.

**Reproduced three ways** (see full auditor transcript for detail):
1. Generic `exec.CommandContext` repro confirming Go's cancel-before-Wait behavior.
2. Confirmed the mechanism in Go stdlib (`Cmd.watchCtx`).
3. **Direct reproduction against the real installed Codex CLI 0.145.0**: replicating
   `connectProcess`'s exact pattern, a write to the child's stdin right after
   `connect()` "succeeds" fails immediately with `write |1: broken pipe` — the
   child was already killed.

**Why it wasn't caught**: `appserver_provider_test.go` only wires `connect` to a
hand-rolled fake (`connectFake`) — `connectProcess` itself is never exercised by
any test. The version-gated E2E test exercises `appserver.StartProcess`/`Client`
directly with its own correctly-scoped `ctx`, bypassing the buggy wiring entirely.
`make commit` runs in `-short` mode, which skips the E2E test, so the gate never
touches the real-subprocess path.

**Cascading effect**: `app_server` mode fails on effectively every real invocation
(for the wrong reason — self-inflicted kill, not genuine absence/incompatibility),
and `auto` mode will therefore always silently fall back to `files` against a real
`codex` binary, defeating the feature. The build's own flagged uncertainty
("no orphan process — reasonably believed, not independently proven") was
investigated by the auditor and found to be sound (`Close()`/kill logic is fine);
the actual defect is the opposite failure mode — the process is killed too early.

**Suggested fix direction** (not applied — routing to human per no-retry-loop
policy): the `context.WithTimeout` used to bound `Initialize()`/process-start must
not be the same context (or at least not `defer cancel()`'d in the same scope)
that outlives the connector — the returned `io.Closer` should own cancellation of
a context that stays live until `Close()`/`Wait()` actually run, e.g. store `cancel`
on the returned closer type and call it from `Close()` instead of deferring it in
`connectProcess`.

Diff (including the earlier-session's fix for the hanging-test/write-blocking bug
and a genuine correction to the archived-filter two-pass semantics) is left
uncommitted in the worktree for inspection/fix once a human picks this up.
