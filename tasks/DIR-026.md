## Finding

The existing Codex E2E test verifies a custom archive installer that copies files into `~/.codex/plugins/meta-cc`, but it does not exercise the current Codex plugin manager. With Codex CLI 0.145, a local marketplace installation succeeds through:

`codex plugin marketplace add <bundle>` followed by `codex plugin add meta-cc@meta-cc-marketplace`

Minimal MCP registration also succeeds through:

`codex mcp add meta-cc -- <absolute-path>/meta-cc-mcp`

The current installation guide emphasizes manual copying and leaves unclear which method is preferred, how skills and MCP configuration are discovered, whether duplicate MCP registrations are created, and that an already-running Codex session cannot hot-load newly installed tools.

## Proposal

Make the supported Codex installation path executable and continuously tested against the current CLI, while retaining a clearly labeled manual/minimal fallback.

### Contract

- The preferred path installs the release bundle through the Codex plugin marketplace commands into an isolated `CODEX_HOME`.
- The test verifies plugin enablement, skill discovery, the resolved MCP command, and a successful live MCP `tools/list`/Codex query from the installed artifact.
- The minimal `codex mcp add` path is documented and tested as a fallback for users who only want the MCP server.
- Installation must not create two active `meta-cc` MCP entries or depend on files outside the isolated home/bundle.
- Documentation must state that a new Codex session is required after installation.

### Design constraints

Detect the installed Codex CLI and skip with an explicit reason only when the required plugin commands are genuinely unavailable; do not silently pass a partial test. Pin or record the tested CLI compatibility range without downloading arbitrary executables during CI. Use temporary homes and local bundles so the test never mutates the developer's real Codex configuration.

### Alternatives considered

- Continuing to test only manual copying does not validate the user-facing plugin workflow.
- Registering both the plugin MCP and a global MCP entry by default risks duplicate tool servers.
- Editing the configuration of the currently running Codex process cannot make it hot-load a new server.

## Plan

1. Add an isolated test harness that builds a local release bundle, creates a temporary `CODEX_HOME`, and invokes the real Codex CLI marketplace/add/list commands when supported.
2. Assert the installed plugin version, enabled state, skill files, MCP resolution, absence of duplicate registration, and live MCP behavior. Keep fixtures synthetic and local.
3. Add a separate minimal-MCP scenario using `codex mcp add`; verify it can start the packaged binary and that uninstall/cleanup is confined to the temporary home.
4. Reconcile `scripts/install/install.sh`, package layout, `.codex-plugin` metadata, `.codex-mcp.json`, and release smoke checks with the preferred plugin-manager path.
5. Rewrite the Codex installation/troubleshooting sections with preferred, minimal, verification, upgrade, restart, and uninstall flows.
6. Run the Codex E2E target, release packaging smoke checks, and repository commit gate.

## Acceptance Criteria

- [ ] An isolated Codex 0.145-compatible plugin install succeeds from a locally built meta-cc bundle.
- [ ] Installed skills and MCP server are discoverable and a live request succeeds.
- [ ] Preferred installation yields exactly one active `meta-cc` MCP registration.
- [ ] Minimal MCP-only installation is independently executable and documented.
- [ ] No test changes the user's real `~/.codex` or running Codex session.
- [ ] Documentation explicitly requires starting a new Codex session after install/update.

## Definition of Done

- [ ] `make test-e2e-codex` covers the supported plugin-manager path or invokes a dedicated target that does.
- [ ] Release smoke checks validate the same bundle layout used by Codex.
- [ ] `make commit` passes.
