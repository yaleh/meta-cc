# validate-artifacts.sh's "combined package: CI smoke tests pass" check fails (23/24) — Phase-4 packaging never copies the Codex plugin files

## Finding

Discovered during DIR-052's adversarial audit (fresh-context, independently reproduced twice —
once on the DIR-052 worktree and once on a pristine HEAD worktree at the same commit, with
IDENTICAL results, proving this is pre-existing and unrelated to DIR-052's LDFLAGS change):

`tests/validation/validate-artifacts.sh` exits non-zero, passing only 23 of 24 checks. The single
failure is:

> "combined package: CI smoke tests pass"

Root cause per the audit: the script's simplified Phase-4 "combined package" assembly is missing
9 Codex plugin files that the CI smoke test requires — `.codex-plugin/` (directory), `skills/`,
and `.codex-mcp.json` are never copied into the combined package the smoke test validates against.
The Phase-1 binary build/exec/install checks all pass in both runs; only this packaging-completeness
check fails.

Evidence this is pre-existing (not caused by any recent change):
- Pristine `main` HEAD worktree (same commit `fecd9c1`, OLD pre-DIR-052 code): 23/24, identical
  single failure.
- DIR-052 worktree: 23/24, identical single failure.
- The failure is in Phase-4 packaging assembly, a code path DIR-052 never touched.

This means `tests/validation/validate-artifacts.sh` currently cannot give a clean bill of health on
ANY commit — it always exits non-zero — which defeats its purpose as a release-readiness validator
and means any future CI wiring of this script will fail out of the gate.

## Proposal

1. Fix the script's Phase-4 combined-package assembly to copy the missing Codex plugin files
   (`.codex-plugin/`, `skills/`, `.codex-mcp.json`) from `plugin-src/` into the combined package,
   mirroring what `make bundle-release` already does correctly (the Makefile's bundle-release target
   copies `.codex-plugin/*`, `skills/*`, `.codex-mcp.json` — the script's simplified copy of that
   logic drifted).
2. Re-run the full script and confirm 24/24.
3. If the script is meant to stay in sync with `make bundle-release`'s packaging logic, consider
   having it delegate to `make bundle-release` (or a shared packaging function) rather than
   maintaining its own simplified copy — the same single-source-of-truth lesson DIR-052 just applied
   to LDFLAGS.
