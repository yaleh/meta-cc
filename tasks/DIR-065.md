# Codex per-turn token usage is overwritten (not accumulated) on each token_count event → systematic undercount

## Finding

In the Codex rollout parser, `applyTokenUsage` assigns the turn's `TokenUsage` from the latest `token_count` event's `last_token_usage`, overwriting any previous value. Codex emits one `token_count` event per model API call, and a tool-using turn makes ≥2 API calls; keeping only the final call's per-call usage discards every earlier call in the turn. The per-turn `usage` surfaced via `Normalize` is therefore systematically low (often ~half) for any tool-using turn. The cumulative `total` path is correct — only the per-turn aggregation is wrong.

Source — `internal/provider/codex/rollout.go:496-512`:
```go
func (b *turnBuilder) applyTokenUsage(timestamp string, last, total codexTokenUsage) {
    b.ensureTurn("", timestamp)
    if last.InputTokens != 0 || last.OutputTokens != 0 || ... {
        b.current.TokenUsage = conversation.TokenUsage{   // OVERWRITES on every token_count event
            InputTokens:  last.InputTokens,
            OutputTokens: last.OutputTokens,
            CacheTokens:  last.CachedInputTokens,
        }
    }
    if total.InputTokens != 0 || ... {
        b.totalTokenUsage = conversation.TokenUsage{       // cumulative — correct
            InputTokens:  total.InputTokens, ...
        }
    }
}
```
`Normalize` emits `b.current.TokenUsage` as the record's `usage` (records.go), so the undercount reaches the `query_session_signals(type=tokens)` / per-turn token output that callers use for cost/usage analysis.

Concrete shape: a turn with two API calls reporting `last` = {in:100,out:50} then {in:80,out:40} ends with `TokenUsage{in:80,out:40}` instead of the turn's consumed {in:180,out:90}. The session `total` (from `total_token_usage`, cumulative) is right, so per-turn figures disagree with the total — an internal inconsistency a caller can observe.

## Proposal

1. Accumulate per-turn usage across the turn's `token_count` events: `b.current.TokenUsage.InputTokens += last.InputTokens` (and output/cache), resetting on a new turn (`ensureTurn`/turn boundary), instead of overwriting.
   - If Codex semantics are that `last_token_usage` is already cumulative-within-turn (not per-call), then instead document that and keep the overwrite — but verify against real rollouts and add a test pinning the chosen semantics. (The cumulative `total` field strongly implies `last` is per-call.)
2. Add a regression test feeding a turn with ≥2 `token_count` events and asserting the per-turn `usage` equals the sum, and that `sum(per-turn) == total` for a single-turn session.

- [ ] For a single-turn session, the sum of per-turn `usage` equals the session `total` (internal consistency).
