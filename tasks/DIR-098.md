## Finding

Dogfooding session (2026-07-30): a corrupt session file (`8eda8f4e-2c74-4176-ba6b-8c45e890df42.jsonl`, "no Claude entries" — empty/truncated) sat undetected in the project session directory until it hard-crashed `query_sessions` (twice) on 2026-07-30. `get_session_directory` and `inspect_session_files` do not surface empty/unparseable files as data — the failure stayed a surprise instead of being discoverable before any query ran.

Structural root cause: DIR-018 (done) fixed skip-and-report tolerance in the analysis `loadData` path, but that behavior was lost/not propagated when DIR-032/DIR-034 rewrote and re-wired the ListSessions path behind `query_sessions`. The discovery tools enumerate files without reporting their health, so consumers keep learning about corruption at crash time.

## Dependencies

## Evidence

One shared probe decides file health: `internal/provider/health.go` — `FileHealth` (`{file, bytes, entries, parseable, empty, error?}`), `ProbeFileHealth(file, kind)`, `MalformedFiles(files, kind)`, `MalformedFilesFromHealth`. The malformed verdict is not re-derived there: it delegates to `locator.ExclusionFor` (the DIR-094 rule already used by `query_sessions` and the analysis loaders), so every corpus-enumerating tool keeps reaching the same conclusion about the same file. `kind` separates `KindClaudeSession` (entries = lines decoding to a `types.SessionEntry` with `IsMessage()`, i.e. exactly `parseClaudeEntries`' rule) from `KindRaw` (Codex rollouts are not Claude-shaped; only readability is judged, otherwise every healthy rollout would read as "empty of messages").

Both handlers consume it — `get_session_directory` calls `provider.MalformedFiles` directly; `inspect_session_files` reaches the same probe through `queryfiles.InspectFiles`, which no longer aborts the batch on one bad file (its `(*InspectionResult, error)` became `*InspectionResult`, since per-file problems are now data, not failure).

**Two judgments, deliberately separate.** *Naming* a defect and *excluding* a file are different verdicts. A file with an unparseable line that still yields message entries is reported defective (`parseable:false`, `error:"1 of 3 non-empty lines are not valid JSON…"`) but is **not** listed in `malformed_files`, because the Claude listing parser tolerates that line and keeps the session. Excluding it would have invented a second, disagreeing rule. Pinned by `TestProbeFileHealth_DefectiveButContributingIsNamedYetNotExcluded`.

**AC verification** (`go test ./...` and `make commit` both exit 0 in this worktree):

- **AC1 + AC3** — dogfood against a read-only copy of this machine's real project corpus (99 real session files) plus the `8eda8f4e-2c74-4176-ba6b-8c45e890df42.jsonl` shape restored as an empty file. `get_session_directory` returned `malformed_files: [{"file": "…/8eda8f4e-….jsonl", "reason": "contains no message entries (empty or metadata-only session stub)"}]`, and `inspect_session_files` named the same file with the same reason. No `query_sessions` call anywhere in that path — the finding is discoverable from Stage 1 alone. Hermetic counterparts: `TestHandleGetSessionDirectory_NamesMalformedFilesWithReasons`, `TestHandleInspectSessionFiles_MalformedCorpus_StructuredHealthNotError`.
- **AC2** — the same real 98-file corpus with the offender removed reports `malformed_files: []` (non-nil, so it serializes as `[]` not `null`) with `file_count`, `total_size_bytes`, `oldest_file`, `newest_file`, `provider`, `scope`, `subagent_file_count` all unchanged. Hermetic counterpart: `TestHandleGetSessionDirectory_HealthyCorpus_SameOutputPlusEmptyMalformedFiles`.
- **AC4** — `InspectFiles` never errors per file. A truncated fixture reports `parseable:false` + `error:"1 of 1 non-empty lines are not valid JSON (truncated or corrupt file)"`; a non-existent file reports `parseable:false` + a stat error and is still listed in `Files` and `malformed_files`; a healthy file beside it is inspected in full (`TestInspectFiles_OneBadFileDoesNotEraseTheRest`). The pre-existing test that asserted the opposite (`TestInspectFiles_NonExistentFile`, and the `"failed to inspect files"` assertion in `stage_validation_test.go`) encoded the fail-fast behavior this task replaces and was rewritten to the new contract.

Three distinct reasons, not one generic string: an empty file gets the DIR-094 empty/metadata-only-stub clause; a truncated file gets the bad-lines clause (so the two do not collapse into one message, asserted in `TestHandleGetSessionDirectory_NamesMalformedFilesWithReasons`); an unreadable file gets the stat/open cause.

The codex branch was extended for consistency (`malformed_files` on `buildCodexDirectoryResult`, `KindRaw`): a rollout that cannot even be `stat`ed was previously dropped from `files` in silence, and is now named.
