## Finding

Reproduced live during this session (2026-07-28) while reinstalling meta-cc to user scope and pointing Codex at the user-scope install instead of the dev repo:

1. **`make stage` fails with "Text file busy" when a running MCP server process holds the target binary open.** `stage:` (`Makefile`) does `cp bin/$(MCP_BINARY_NAME) plugin-src/bin/$(MCP_BINARY_NAME)` — an in-place overwrite of an executable that may currently be mapped/executing under a live MCP server process (e.g. a Codex dev-mode session registered directly against `plugin-src/bin/meta-cc-mcp`, or any other long-running consumer). `cp`'s open-and-truncate-in-place semantics collide with the kernel's ETXTBSY protection for a running executable. Today this required manually finding and `kill`-ing PID 1406569 (a Codex MCP server process holding `plugin-src/bin/meta-cc-mcp` open) before `make install-user` could proceed — an unnecessary manual step and, in a less obvious case, a source of confusing build failures for any contributor who has a plugin session open in another terminal.

2. **`install-user` only registers the plugin for Claude Code, not Codex — the two integrations silently drift.** `install-user:` (`Makefile`) rsyncs `plugin-src/` to `~/.local/share/meta-cc/` and updates `~/.claude/settings.json`'s `extraKnownMarketplaces`/`enabledPlugins` to point Claude Code at the user-scope copy. It does nothing for Codex's own registration (`~/.codex/config.toml`'s `[marketplaces.meta-cc-marketplace]` `source`), which a developer typically points at the repo directly for local dev (`source_type = "local"`, `source = "/home/yale/work/meta-cc"`). Running `make install-user` therefore leaves Codex silently running the dev-mode binary straight out of the repo (`plugin-src/bin/meta-cc-mcp`) even after a "user scope" install — the two clients end up on different binaries with no warning. Today this required a manual, undocumented edit of `~/.codex/config.toml` to repoint Codex's `source` at `~/.local/share/meta-cc`.

## Proposal

1. Make `stage`'s binary copy resilient to a live-locked destination: write to a temp file in the same directory (e.g. `plugin-src/bin/$(MCP_BINARY_NAME).tmp.$$`) and `mv` it into place. `mv` (rename) atomically replaces the destination inode without requiring the old inode to be writable/truncatable, so any process still holding the old binary open keeps running the old (now-unlinked) copy until it exits, and `stage` never fails with ETXTBSY.
2. Extend the install path so Codex's own registration can be kept in sync with the user-scope install, analogous to what `install-user` already does for `~/.claude/settings.json`:
   - Either fold a Codex-registration step into `install-user` (guarded so it's a no-op if `~/.codex/config.toml` doesn't exist or has no `meta-cc-marketplace` entry), or add a clearly-documented sibling target (e.g. `install-user-codex`) that a developer runs once.
   - `~/.codex/config.toml` is TOML, not JSON — the existing `jq`-based merge pattern used for `~/.claude/settings.json` does not apply directly; the fix needs a TOML-safe update (e.g. a small Python `tomllib`/`tomli-w` snippet, or a minimal Go/Node helper checked into `scripts/`) that only touches the `[marketplaces.meta-cc-marketplace]` table's `source`/`source_type` keys and leaves the rest of the file (other marketplaces, model providers, etc.) untouched.
   - Print an explicit confirmation of what changed (old source → new source), mirroring `install-user`'s existing `✓ Updated ~/.claude/settings.json` style output.

## Contract

- `make stage` succeeds even when the previous `plugin-src/bin/$(MCP_BINARY_NAME)` is held open by a running process (e.g. a live MCP server), and does not corrupt or truncate the binary any in-flight process is currently executing.
- Running the Codex-registration step points `~/.codex/config.toml`'s `[marketplaces.meta-cc-marketplace]` `source` at the user-scope install path (`$HOME/.local/share/meta-cc`) without disturbing any other TOML content in the file (other `[marketplaces.*]`, `[plugins.*]`, `[model_providers.*]`, `[projects.*]` entries, comments, formatting elsewhere).
- No behavior change for a developer who never touches Codex or never has a live MCP process locking the binary — both fixes are additive safety/coverage, not a change to the normal happy path.

## Plan

1. Reproduce failure 1: start a long-lived process holding `plugin-src/bin/meta-cc-mcp` open (e.g. `plugin-src/bin/meta-cc-mcp &`), then run `make stage` and confirm it fails with "Text file busy".
2. Change `stage`'s copy step to write-to-temp + `mv`; re-run the same repro and confirm `make stage` now succeeds while the held-open process keeps running unaffected (verify via `ps`/`lsof` that the old process's fd still resolves to the old unlinked inode, and a fresh spawn of the binary reflects the new one).
3. Reproduce failure 2: with `~/.codex/config.toml` containing a `[marketplaces.meta-cc-marketplace]` block pointed at the repo path, run `make install-user` and confirm the Codex config is left untouched (still pointing at the repo).
4. Implement the TOML-safe Codex-registration step (new target or folded into `install-user`); re-run and confirm `~/.codex/config.toml`'s `source` now reads `$HOME/.local/share/meta-cc`, with every other line in the file byte-for-byte unchanged (diff before/after minus the one field).
5. Add a lightweight test (Bats or Go, matching existing `tests/e2e/codex-*.sh` conventions) covering both: (a) `stage` succeeding against a locked destination, (b) the Codex TOML update only touching the intended keys.
6. Document the new/changed target(s) in `docs/guides/plugin-development.md` and/or `docs/guides/release-process.md`.

## Acceptance Criteria

- [ ] `make stage` succeeds when the current `plugin-src/bin/meta-cc-mcp` is held open by a running process (reproduced and verified, not just asserted).
- [ ] A Codex-registration step exists (as part of `install-user` or a new documented target) that updates `~/.codex/config.toml`'s `[marketplaces.meta-cc-marketplace]` `source` to the user-scope install path, verified to leave all other TOML content unchanged.
- [ ] Both behaviors are covered by an automated test, not just manual verification.
- [ ] `make commit` passes.

## Definition of Done
