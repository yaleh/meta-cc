## Finding

`query_session_signals`'s MCP tool schema declares a `status` parameter specifically for
`type="tool_stats"`, documented as: `"When type=tool_stats: filter by status (error/success)"`
(`internal/mcp/tools/tools.go:403-406`, inside the `query_session_signals` `BuildTool(...)` call at
line 392). The parameter is present on every call the schema advertises and is the only
documented way to narrow `tool_stats` results to just failing or just succeeding tool calls.

The actual `type="tool_stats"` implementation, `handleQueryTools`
(`internal/mcp/executor/handlers.go:74-90`), never reads it:

```go
func handleQueryTools(e *ToolExecutor, scope string, args map[string]interface{}) (mcquery.QueryResult, error) {
	providerName := GetStringParam(args, "provider", "claude")
	toolName := GetStringParam(args, "tool", "")
	limit := GetIntParam(args, "limit", 0)
	workingDir := GetStringParam(args, "working_dir", "")
	includeSubagents := GetBoolParam(args, "include_subagents", true)

	jqFilter := `select(.type == "assistant") | select(.message.content[] | .type == "tool_use")`

	if toolName != "" {
		escapedTool := EscapeJQ(toolName)
		jqFilter = fmt.Sprintf(`%s | select(.message.content[] | select(.type == "tool_use" and .name == "%s"))`, jqFilter, escapedTool)
	}

	sessionID := GetStringParam(args, "session_id", "")
	return e.dispatchProviderQuery(providerName, scope, jqFilter, limit, workingDir, sessionID, mcquery.ParsedTimeRange{}, includeSubagents)
}
```

`args["status"]` is never referenced anywhere in this function, nor anywhere else in the codebase
outside `tools.go`'s schema declaration:

```
$ grep -rn "GetStringParam(args, \"status\"" internal/mcp/ --include=*.go | grep -v _test
internal/mcp/executor/query_sessions_handler.go:347:  Status: GetStringParam(args, "status", ""),
```

— the only production read of a `"status"` arg anywhere in `internal/mcp` belongs to the unrelated
`query_sessions` Codex `archived`/`status` filter, not `query_session_signals`'s `tool_stats`
branch.

**Reproduced live against this project's own session history** (`/home/yale/work/meta-cc`,
2026-07-28), four calls to `query_session_signals(type="tool_stats", provider="all",
stats_only=true)`, varying only `status`:

| `status` value | `session_count` | `total` | hourly histogram |
|---|---|---|---|
| *(omitted)* | 7 | 312 | 44 buckets, e.g. `{"count":36,"hour":"2026-07-28T09"}` |
| `"error"` | 7 | 312 | byte-identical 44 buckets |
| `"success"` | 7 | 312 | byte-identical 44 buckets |
| `"bogus-value-xyz"` | 7 | 312 | byte-identical 44 buckets |

All four calls return the exact same `session_count`, `total`, and per-hour bucket counts —
`status="error"` does not narrow to failures, `status="success"` does not narrow to successes, and
even a nonsense value like `"bogus-value-xyz"` is silently accepted and produces the identical
result instead of erroring. This directly contradicts the fail-closed contract this same MCP
surface's own filtering work already committed to: DIR-030's own `## Contract` section (this
repo's `tasks/DIR-030.md`) states "Invalid or unsupported filters fail closed with actionable
errors" — `status` currently does neither: valid values don't filter, and invalid values don't
fail.

This is distinct from the two already-fixed no-op parameter defects on this same MCP surface
(`tasks/DIR-041.md`'s `jq_filter` no-op across the four consolidated tools, and `tasks/DIR-042.md`'s
`stats_only` no-op on 5 of 6 `analysis.Service` tools) — this is a *different* parameter
(`status`), on a *different* handler (`handleQueryTools`, not `analysis.Service` or
`BuildResponse`'s `JQFilter`/`StatsOnly` fields), on a *different* tool signal type (`tool_stats`
under `query_session_signals`).

## Proposal

1. In `handleQueryTools` (`internal/mcp/executor/handlers.go:74-90`), read
   `status := GetStringParam(args, "status", "")` and, when non-empty, append a jq clause that
   narrows to matching tool-call outcomes — e.g. joining the following `tool_result`'s `is_error`
   field for the same tool_use id (mirroring how `handleQueryToolErrors` at the same file's line 92
   already filters on `.is_error == true` for a related but different query shape), or an
   equivalent mechanism that actually distinguishes error vs. success tool calls.
2. Validate `status` against the two documented values (`"error"`, `"success"`) and return an
   actionable error for anything else, per the DIR-030 fail-closed contract this repo has already
   committed to elsewhere on this same MCP surface.
3. Add a regression test proving `status="error"` and `status="success"` produce measurably
   different (and correctly filtered) result sets against a fixture with both outcomes present.
