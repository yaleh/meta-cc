## Finding

`query_session_content`, `query_session_signals`, `query_sessions`, and `query_file_activity` all
declare a `jq_filter` parameter in their MCP tool schema ("jq expression for filtering. Defaults to
`.[]` when omitted"), and CLAUDE.md's own FAQ/documentation treats `jq_filter`-style custom
filtering as a first-class, working capability of the query surface. In the actual implementation,
this argument is read into a config struct and then **never applied to the query result** — it is
a pure no-op for all four tools.

Reproduced live in this session, three separate ways, all against `provider="all"` over this
repo's own session history (`/home/yale/work/meta-cc`, 2026-07-28):

1. `query_session_content({role: "assistant", provider: "all", jq_filter: "select(false)"})` —
   a jq filter that must yield **zero** records under any correct jq implementation — returned all
   **579** unfiltered records (verified in three modes: default, `stats_only: true`, and
   `stats_first: true`; all three returned the identical 579-record/579-hour-bucket result as the
   call made with no `jq_filter` at all).
2. `query_session_signals({type: "tool_stats", provider: "all", jq_filter: "select(false)"})` —
   returned all **297** unfiltered records (`file_ref` with `record_count: 297`, `returned_records:
   297`), identical to the same call without `jq_filter`.
3. `query_sessions({provider: "all", jq_filter: "select(false)"})` — returned all **9** unfiltered
   session records (`returned_records: 9`), including full titles/cwd/model metadata, identical to
   the same call without `jq_filter`.

Root cause, confirmed by reading the source:

- `internal/mcp/executor/executor.go:36` — `NewToolPipelineConfig` builds
  `pipelinepkg.PipelineConfig{JQFilter: GetStringParam(args, "jq_filter", ".[]"), ...}`, i.e. it
  does read the caller-supplied `jq_filter` argument into the `JQFilter` field.
- `internal/mcp/pipeline/pipeline.go:30` declares `JQFilter string` on `PipelineConfig`, consumed
  by `BuildResponse` (`pipeline.go:54`).
- A repo-wide grep confirms `JQFilter` is referenced in exactly two `.go` locations outside tests —
  its declaration (`pipeline.go:30`) and its one assignment (`executor.go:36`):
  ```
  $ grep -rn "JQFilter" internal --include=*.go | grep -v _test.go
  internal/query/engine/jq.go:13/14   (an unrelated helper, ApplyJQFilter, not wired to this struct)
  internal/query/pipeline/types.go:13 (a different, unrelated PipelineConfig in a sibling package)
  internal/mcp/executor/executor.go:36
  internal/mcp/query/query.go:53      (a third, unrelated QueryOptions.JQFilter, used only by
                                        execute_stage2_query's own separate code path)
  internal/mcp/pipeline/pipeline.go:30
  ```
  `internal/mcp/pipeline/pipeline.go`'s own `BuildResponse` function body never reads
  `pc.JQFilter` — the field is write-only. Each of the four tools instead builds its own
  hard-coded, semantically-fixed jq expression internally (e.g.
  `internal/mcp/executor/handlers.go:45-67` for `query_session_content`, based on `role`/
  `pattern`/`contains`/etc.) and passes *that* string down through `dispatchProviderQuery` —
  the caller's own `jq_filter` argument from the tool call never enters this internal string at
  all.
- This is a different, unrelated, and correctly-working code path from `execute_stage2_query`
  (`internal/mcp/query/query.go:53`'s `QueryOptions.JQFilter`), which is why the Two-Stage Query
  Guide's own `execute_stage2_query` examples work — the defect is specific to the four
  consolidated Stage-1 tools accepting the same-named parameter but not honoring it.

This silently converts what looks like a targeted, safe query (e.g. "give me only entries where
X") into "return the entire unfiltered result set" — a false sense of narrowing that could cause a
caller to draw wrong conclusions from what looks like a filtered result, or to unexpectedly receive
much larger output than expected/budgeted for.

## Proposal

1. Either wire `PipelineConfig.JQFilter` into `BuildResponse` as an actual post-filter stage
   (applying the caller's jq expression to the already-produced result set, composed after each
   tool's own internal semantic filter, mirroring how `execute_stage2_query`'s `QueryOptions.JQFilter`
   already works), or, if custom jq filtering is intentionally not supported on these four
   consolidated tools (callers should use `execute_stage2_query` instead), remove the `jq_filter`
   parameter from their MCP tool schemas and documentation so it stops being advertised as
   functional.
2. Whichever direction is chosen, add a regression test that would fail today: a `jq_filter` value
   that provably changes/empties the result set (e.g. `select(false)`) must produce a
   correspondingly changed/empty result for all four tools — not the full unfiltered set.
3. Audit `docs/guides/mcp-query-tools.md` and the MCP tool schema descriptions so the documented
   contract for `jq_filter` on these four tools matches whichever behavior is implemented.
