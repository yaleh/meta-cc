# Codex dot-schema `item.tool_result` omits ensureTurn → nil-pointer panic crashes the server

## Finding

In the Codex rollout parser's dot-schema (`schemaNew`) dispatch, the `item.tool_result` case appends to `b.current.Items` without first ensuring a turn exists. Every sibling case guards with `b.ensureTurn(...)`; this one does not. When `b.current == nil`, `appendToolResultItem` dereferences a nil pointer and panics. There is no `recover()` in `internal/` or `cmd/`, so the panic crashes the MCP server for the whole request.

Source — `internal/provider/codex/rollout.go`:
```go
// rollout.go:553-561 — item.tool_call GUARDS
case "item.tool_call":
    ...
    b.ensureTurn("", event.Timestamp)          // line 560
    b.appendToolCallItem(...)

// rollout.go:562-569 — item.tool_result does NOT guard
case "item.tool_result":
    var payload struct { ID, Output string; IsError bool ... }
    _ = json.Unmarshal(event.Payload, &payload)
    b.appendToolResultItem(payload.ID, payload.Output, payload.IsError, event.Timestamp)  // line 569
```
```go
// rollout.go:224-233 — appendToolResultItem dereferences b.current unguarded
func (b *turnBuilder) appendToolResultItem(callID, output string, isError bool, timestamp string) {
    ts, _ := time.Parse(time.RFC3339, timestamp)
    b.current.Items = append(b.current.Items, conversation.Item{...})   // nil deref if b.current == nil
}
```
The `item.message` case calls `ensureTurn` at line 541 and `item.tool_call` at line 560; the legacy `response_item` output path also ensures a turn. Only `item.tool_result` (line 562-569) omits it. `b.current` is set to nil by `flush()` (invoked from `turn.completed` at line 570-574), so the window is real.

Trigger: a dot-schema rollout where an `item.tool_result` is the first record of the file, or arrives after a `turn.completed` (which flushes → `b.current = nil`). This happens with head-truncated/rotated rollout files, a late/duplicate notification line, or a resumed stream — all plausible for a live Codex session. Result: panic crashes the request instead of degrading gracefully.

This is distinct from the filed Codex lifecycle findings (DIR-050 flush() drop, DIR-053 Normalize drop) — those are about *dropped turns*; this is a *panic* on a missing guard.

## Proposal

1. Add `b.ensureTurn("", event.Timestamp)` at the top of the `item.tool_result` case (rollout.go:569), matching the `item.tool_call`/`item.message` cases — the minimal, consistent fix.
2. Defensively, make the `append*Item` helpers call `ensureTurn` themselves (or nil-guard `b.current`) so no future event case can reintroduce the crash.
3. Add a dispatch-level `recover()` so any unforeseen parser panic degrades to a warning + skipped record rather than killing the server.
