## Finding

`internal/mcp/response/adapter.go:17` reads an `output_mode` parameter to control inline vs file_ref response mode, but `output_mode` is declared in NO tool schema: neither `StandardToolParameters` (`internal/mcp/tools/tools.go:16-56`) nor any individual tool definition includes it. `ValidateToolArgs` (`tools.go:657-665`) rejects undeclared parameters and `ExecuteTool` (`internal/mcp/executor/executor.go:119`) validates before the pipeline, so passing `output_mode` through any real tool call ALWAYS hard-errors. The parameter is dead code in production; existing tests only exercise it by bypassing `ExecuteTool` and calling `adaptResponse` directly (`cmd/mcp-server/integration_test.go:241,360`; `response_adapter_test.go:232,396`).

## Proposal

Pick ONE of two resolutions (implementer's choice, prefer A if the hybrid-output UX justifies it):

A. **Register the parameter**: add `output_mode` (enum: `inline`, `file_ref`, `auto` — default `auto`, preserving current behavior) to `StandardToolParameters` so every tool accepts it, and update the adapter tests to go through `ExecuteTool` validation.
B. **Remove the dead code**: delete the `output_mode` read from `adapter.go` and update the bypassing tests to match real schema behavior.

Either way, tests must reflect actual schema-enforced behavior, not a bypass path.

## Plan

1. Choose resolution A or B (document the choice in the commit message).
2. Implement: schema registration + validation-passing tests, OR dead-code removal + test updates.
3. Verify a real MCP tool call with `output_mode` behaves per the chosen resolution.
