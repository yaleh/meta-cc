# Unbounded page_size/offset integer overflow panics the MCP server (DoS)

## Finding

`internal/filter/pagination.go` computes the slice end as `start + pageSize` with no upper-bound or overflow check. A large `page_size` combined with a modest `offset` overflows a signed `int` negative, and the subsequent `data[start:end]` panics with "slice bounds out of range". There is no `recover()` anywhere in `internal/` or `cmd/`, so the panic crashes the MCP server process — a denial of service triggerable by any client.

Source — `internal/filter/pagination.go:64-74` (`ApplyPaginationToInterfaces`):
```go
start := normalizedOffset
end := totalRecords
if pageSize > 0 {
    end = start + pageSize        // line 68 — signed overflow → negative
    if end > totalRecords {       // false when end is negative
        end = totalRecords
    }
}
return data[start:end], meta      // data[2000:-9223372036854774832] → panic
```
The identical overflow exists in the `ToolCall` variant `ApplyPagination` at `pagination.go:37` (`end = start + config.Limit`). `CalculateMetadata`'s `config.Offset+config.Limit` (line 96) overflows too (corrupts `has_more`).

Reachability: all four consolidated query tools (`query_session_content`, `query_session_signals`, `query_sessions`, `query_file_activity`) accept `offset`/`page_size` via `StandardToolParameters` and flow through `NewToolPipelineConfig` (`internal/mcp/executor/executor.go`, `GetIntParam` does a raw `int(float64)` with no range validation) → `pipeline.BuildResponse` → `ApplyPaginationToInterfaces`. `ValidateArgKeys` only checks key presence, never numeric bounds. This pagination was wired by DIR-004 ("file_ref mode should support streaming or pagination", done) — that task added the parameters but no bounds validation.

Reproduced with a standalone copy of the exact arithmetic (`/tmp/claude-1000/repro/main.go`):
```
$ go run .
[pagination] offset=2000 page_size=9223372036854774784 over 3000 records => PANIC: runtime error: slice bounds out of range [:-9223372036854774832]
[pagination] start+pageSize = -9223372036854774832 (negative => data[2000:neg] panics)
```
`9223372036854774784` = 2⁶³−1024, exactly representable as a JSON float64, so it survives the JSON→`float64`→`int` round trip. Trigger against the live server: any query matching ≳2000 records (trivial at `scope=project`) with `{offset: 2000, page_size: 9223372036854774784}`.

Recurrence pattern: the codebase has no centralized numeric-bounds validation for pagination params; every call site trusts the raw int. Negative offset is clamped (lines 23-25, 52-54) but overflow on the upper end is not, so the "defensive" clamping gives false confidence.

## Proposal

1. Clamp/sanitize in one place: before computing `end`, cap `pageSize` and `offset` to `[0, totalRecords]` (or a sane hard max), and compute the end without overflow, e.g. `end := totalRecords; if pageSize > 0 && pageSize < end-start { end = start + pageSize }`. Apply to both `ApplyPaginationToInterfaces` (line 68) and `ApplyPagination` (line 37), and fix `CalculateMetadata`'s `Offset+Limit` (line 96).
2. Add a shared guard in `GetIntParam`/`NewToolPipelineConfig` so no future call site can pass an out-of-range pagination value.
3. Add a top-level `recover()` in the MCP request dispatch (`cmd/mcp-server` / executor) so any unforeseen panic degrades to an error response instead of killing the server.

## Acceptance Criteria

- [ ] `ApplyPaginationToInterfaces(data, 2000, 9223372036854774784)` (len(data)≥2001) does not panic and returns a well-defined page (clamped to the available records).
- [ ] `ApplyPagination` with an overflow-inducing `Limit` does not panic.
- [ ] A unit test in `internal/filter` asserts no panic and correct clamping for `pageSize`/`offset` values at and above `math.MaxInt64`/2 and for negative values.
- [ ] A live `query_session_signals({type:"timestamps", offset:2000, page_size:9223372036854774784})` returns a normal (clamped) response, not a crashed server.
- [ ] `go test ./internal/filter/... ./internal/mcp/...` passes; `make commit` passes.
