## Finding

Claude Code Workflow scripts run in a Bun-compiled JavaScript runtime that does NOT have access to the Claude Code tool API. Calling `Skill()`, `Agent()`, `Bash()`, or any other Claude Code tool from within a workflow script results in `ReferenceError: <tool> is not defined`. Evidence:

- Session `b2520f9f-0f82-4241-b460-b7074b6b9830`, 2026-07-25T16:11:25Z:
  - `Skill({skill:"run-routines", args:"DIR-001"})` dispatched a dynamic workflow titled "Evaluate the standing routine track from .quay/loop.yml — delegates to the quay:run-routines skill"
  - Workflow crashed immediately: `Error: Skill is not defined` at `workflow.js:8:36`
  - The workflow attempted to call `Skill({skill:"quay:run-routines", args:"DIR-001"})` from within workflow code
  - Duration: 24ms, 0 agent tokens — instant failure
  - The workflow's DESIGN was to be a "backward-compat thin wrapper (M140, 2026-07-25)" that delegates to a skill

**Root cause**: The workflow author assumed workflow scripts could invoke skills, creating a delegation pattern: Workflow -> Skill -> Subagents. But the workflow runtime is isolated — it can only dispatch subagents via the workflow DSL, not invoke Claude Code tools.

This is a **design constraint** that needs to be documented as an ADR, not a bug. The isolation is by design: workflows are compiled to Bun, which has no access to the Claude Code runtime. The correct pattern is:
- Workflow dispatches agents directly (not via skills)
- Skills dispatch workflows (one-way bridge)
- Workflows CANNOT call skills

**Recurrence risk**: HIGH for new workflow authors. Without clear documentation, any developer who creates a workflow that tries to reuse an existing skill will hit this error. The `run-routines` workflow was explicitly created as a "thin wrapper" — a natural and reasonable design intent that the platform does not support.

## Proposal

1. **Write ADR-007**: "Workflow-Skill API Isolation" documenting the one-way Skill->Workflow bridge, the constraints on workflow scripts, and the recommended patterns for code reuse
2. **Fix the run-routines workflow**: Remove the `Skill()` call and implement the routine evaluation logic directly in the workflow or via agent dispatch
3. **Add a lint rule**: Detect `Skill(`, `Agent(`, `Bash(`, etc. in workflow scripts at generation time and warn/error

## Plan

### Phase 1: Write ADR-007
- Create `docs/architecture/adr/ADR-007.md` with:
  - **Title**: Workflow-Skill API Isolation
  - **Status**: Accepted
  - **Context**: Workflow scripts run in Bun-compiled JS, not in the Claude Code runtime
  - **Decision**: The Skill->Workflow bridge is one-way. Workflows dispatch agents directly; they cannot invoke skills, bash, or other tools.
  - **Consequences**: Workflow code reuse must happen via shared JS modules imported at compile time, not via skill delegation at runtime.
- Register via `quay adr write`

### Phase 2: Fix run-routines workflow
- Replace the `Skill({skill:"quay:run-routines"})` call with direct agent dispatch or inline logic
- The workflow should read `.quay/loop.yml`, identify the routine track, and dispatch probe agents directly
- This follows the pattern already used by `drain-directives` and `execute-milestone` workflows

### Phase 3: Add workflow linting
- In the workflow generator (or as a pre-commit hook), detect tool API calls in workflow scripts:
  - `/Skill\(/` -> warn: "Skill() is not available in workflow runtime. Dispatch agents directly."
  - `/(Agent|Bash|Read|Write|Edit)\(/` -> warn: "Tool APIs are not available in workflow runtime."
- This catches the pattern at authoring time, not at runtime

### Phase 4: Update documentation
- Add "Workflow Constraints" section to the workflow development guide
- Document the one-way bridge: Skill -> Workflow (yes), Workflow -> Skill (no)
- List available workflow APIs: `agent()`, `result()`, `$()`
