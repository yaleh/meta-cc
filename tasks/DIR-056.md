# ADR-007: record the measured/estimated DataSource provenance convention (and resolve the mixed-provenance collapse)

## Finding

Every analyzer result in meta-cc carries a `data_source` provenance field with values
`"measured"` | `"estimated"`, defined at `internal/analyzer/data_source.go:1-20` as
"BAIME Layer 7 provenance tracking". It is used 36 times across 8 non-test files
(`internal/analysis/service.go`, `internal/analyzer/{bugs_analysis,quality_analysis,
timeline,errors_analysis,work_patterns,tech_debt,data_source}.go`), and appears in the
output of every analysis MCP tool — measured runs in session
`16c504aa-6681-40b0-bfce-4f25f4dce679` (2026-07-28) confirm `analyze_errors`,
`analyze_bugs`, `quality_scan`, and `get_tech_debt` all emit `"data_source":"measured"`.

This is a cross-cutting, reusable design decision — yet it is undocumented: the ADR
index (`docs/architecture/adr/`) contains ADR-001..006 only; none covers provenance,
and no other doc defines what "BAIME Layer 7" means for this codebase (grep finds
`BAIME` only in unrelated Chinese-language analysis docs under `docs/analysis/`).
DIR-009 (todo, "Register existing 6 ADRs in quay task system") would register the six
existing ADRs but cannot register one that does not exist.

The convention also has an unresolved ambiguity already visible in code:
`TechDebtResult`'s doc comment (`internal/analyzer/tech_debt.go:28-32`) states
"OpenIssues uses a heuristic (error call with no subsequent success for the same tool)
and is technically 'estimated'; the top-level DataSource reflects the dominant measured
provenance." So a result can advertise `measured` while shipping an `estimated`
subfield — consumers (including this project's own autonomous loop, which treats
measured data as ground truth) have no reliable way to know which fields are heuristic.
Each new analyzer re-decides this ad hoc, with no written rule and no enforcement.

## Proposal

Author `docs/architecture/adr/ADR-007-provenance-data-source.md` recording:

1. **Decision**: every analysis result type carries a `DataSource` field; `measured`
   means directly counted/aggregated from observable session events; `estimated` means
   heuristic inference (examples: open-issue detection, context-switch proximity —
   `data_source.go:13-19`).
2. **Mixed-provenance rule** (resolves the tech_debt.go:28-32 ad hoc collapse): choose
   ONE of — (a) per-field provenance annotations on any result mixing both, or (b) a
   documented "dominant provenance + `estimated_fields` list" convention — and apply it
   uniformly; update `TechDebtResult` (and any other mixed result) to conform.
3. **Enforcement**: a test (or lint-style gate script consistent with DIR-045's
   static-gate direction) asserting every exported `*Result`/`*Stats` struct in
   `internal/analyzer` has a `DataSource` field, so new analyzers cannot silently omit
   provenance.
4. Register ADR-007 alongside DIR-009's six, and add it to `docs/architecture/adr/README.md`.

## Acceptance Criteria

- [ ] `docs/architecture/adr/ADR-007-provenance-data-source.md` exists using `template.md` structure, names the two enum values, and gives the rationale (consumer trust levels for autonomous-loop consumption).
- [ ] The ADR states an explicit, single mixed-provenance rule; `TechDebtResult`'s doc comment (`tech_debt.go:28-32`) is updated to cite ADR-007 instead of an inline ad hoc policy, and the code conforms (e.g. `OpenIssues` provenance is surfaced per the chosen rule).
- [ ] A test enumerates analyzer result structs and fails if an exported result type lacks a `DataSource` field.
- [ ] `docs/architecture/adr/README.md` index lists ADR-007; DIR-009's registration scope is extended to include it (note in DIR-009, no board write required from this routine).
