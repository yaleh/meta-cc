## Finding

This repo's MCP tool schema layer (`internal/mcp/tools/tools.go`) and its dispatch layer
(`internal/mcp/executor/*.go`, `internal/mcp/pipeline/pipeline.go`) are two independently-edited
places: a `Property` entry in a `BuildTool(...)` call advertises a parameter to callers, but
nothing enforces that the corresponding handler/pipeline code actually reads and acts on
`args["<name>"]`. The same shape of defect — a parameter is declared in the schema, optionally
copied into a config struct field, and then never consulted by the code that produces the
response — has now been found **four separate times** on this exact MCP surface:

1. **`jq_filter`**, on all four consolidated query tools (`query_session_content`,
   `query_session_signals`, `query_sessions`, `query_file_activity`) — filed as `tasks/DIR-041.md`,
   root-caused to `internal/mcp/pipeline/pipeline.go`'s `BuildResponse` never reading
   `PipelineConfig.JQFilter`, now fixed (commit `24d69dd`, "fix(mcp): wire jq_filter into
   BuildResponse as a real post-filter").
2. **`stats_only`**, on 5 of the 6 `analysis.Service`-backed tools (`analyze_bugs`,
   `analyze_errors`, `quality_scan`, `get_work_patterns`, `get_tech_debt`) — filed as
   `tasks/DIR-042.md`, root-caused to `boolArg(args, "stats_only")` being referenced exactly once
   in `internal/analysis/service.go` (inside `GetTimeline`) instead of six times; status `ready`,
   not yet built.
3. **`status`**, on `query_session_signals(type="tool_stats")` — a newly-identified instance (this
   routine run, see the sibling task `tasks/DIR-043.md`): declared at
   `internal/mcp/tools/tools.go:403-406`, never read anywhere in `handleQueryTools`
   (`internal/mcp/executor/handlers.go:74-90`). Reproduced live: `status="error"`,
   `status="success"`, and `status="bogus-value-xyz"` all return the byte-identical
   `session_count:7, total:312` result.
4. **`output_format`**, on all 16 tools via `StandardToolParameters()` — a newly-identified instance
   (this routine run, see the sibling task `tasks/DIR-044.md`): declared at
   `internal/mcp/tools/tools.go:44-47`, read once into `PipelineConfig.OutputFormat`
   (`internal/mcp/executor/executor.go:39`), then never consulted by `BuildResponse`. Reproduced
   live: `query_sessions({output_format: "tsv"})` returns plain JSON, never TSV.

Four instances across three different files (`pipeline.go`, `service.go`, `handlers.go`) and across
both the "consolidated query tools" and "analysis service" halves of the MCP surface shows this is
not a one-off typo pattern — it is a structural gap: **there is no mechanism, automated or manual,
that cross-checks a tool's declared schema properties against the set of parameter names its own
handler code actually reads.** `make lint`'s existing `lint-errors`/`vet`/`check-go-quality` gates
do not catch this because `args["status"]` (an untyped `map[string]interface{}` lookup) is
syntactically valid Go whether or not the key is ever read — there is nothing for `go vet` or
standard linters to flag. Each of the four instances was only found by a human/agent manually
comparing a tool's schema description against its handler source, which is exactly the kind of
check that doesn't scale and that a fifth, sixth, and seventh instance will keep slipping past
without a mechanical gate.

## Proposal

Add a lightweight static check — a Go test or a small script wired into `make lint`/`make
check-go-quality` — that, for every tool registered via `BuildTool(...)` in
`internal/mcp/tools/tools.go`, verifies each declared `Property` name (other than parameters that
are legitimately consumed generically, e.g. `working_dir`, `session_id`, `scope`, `provider`,
`limit`, `offset`, `page_size`, `inline_threshold_bytes`, which already flow through common
plumbing) has at least one corresponding `GetStringParam(args, "<name>"`
/`GetBoolParam(args, "<name>"`/`GetIntParam(args, "<name>"` (or equivalent) call reachable from that
tool's registered handler function, OR is on an explicit, documented allowlist of
intentionally-generic/pass-through parameters. This can be implemented as:

- A source-level static test (parse `tools.go` for `BuildTool` calls + `Property` keys per tool
  name; parse the executor/pipeline packages for `args["<name>"]`/`GetXxxParam(args, "<name>"`
  occurrences reachable from each tool's handler; fail if a declared name has zero occurrences
  outside the allowlist), analogous in spirit to the existing `check-no-scanner` gate
  (`Makefile:621`) that already greps for a banned pattern across the tree.
- Or, more simply to start, a single Go test in `internal/mcp/tools` that enumerates all
  `BuildTool` property names and asserts each appears as a string literal argument to
  `GetStringParam`/`GetBoolParam`/`GetIntParam` somewhere under `internal/mcp/executor` or
  `internal/mcp/pipeline`, with an explicit allowlist constant for the shared/generic parameter
  names.

## Acceptance Criteria

- [ ] A new automated check (Go test and/or shell script wired into `make lint` or
      `make check-go-quality`) exists that, when run against `main` **before** the `status`/
      `output_format` fixes (DIR-043/DIR-044) land, fails and names at least those gaps (or a
      documented subset reproducible at the time this check is implemented).
- [ ] The check passes once `status` (DIR-043) and `output_format` (DIR-044) are fixed or their
      parameters are removed from the schema.
- [ ] A deliberately-reintroduced no-op parameter (e.g. temporarily adding a new unused `Property`
      to one `BuildTool` call in a scratch branch, without wiring a corresponding `GetXxxParam`
      read) causes the new check to fail — verified by an actual run, not narrative claim.
- [ ] The check is wired into a target `make lint`, `make check-go-quality`, or `make push`
      transitively reaches, not merely invokable by name.
- [ ] `go test ./internal/mcp/...` passes.
- [ ] `make commit` passes.

## Definition of Done

- [ ] The new gate is landed on `main`, not left in a worktree, and is part of the normal
      `make lint`/`make push` pipeline so it runs on every future change without a human remembering
      to invoke it manually.
- [ ] The gate's allowlist of intentionally-generic parameter names (e.g. `working_dir`,
      `session_id`, `provider`, `scope`, `limit`) is documented inline (a comment in the
      test/script) so a future contributor understands why those names are exempt rather than
      assuming the gate is incomplete.
- [ ] `docs/guides/mcp-query-tools.md` or a relevant contributor doc briefly notes the existence of
      this gate so a new tool/parameter author knows to expect it.
- [ ] `make commit` passes.
