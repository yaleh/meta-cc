## Finding

`analyze_errors` groups errors `by_type` using opaque SHA hashes (e.g., `00fe62be6467099b: 6x`)
instead of human-readable labels. The by-tool breakdown (`by_tool`) is immediately useful,
but the by-type view is nearly useless without drilling into each example. An agent or human
reading the output cannot distinguish "permission_blocked" from "stale_read" from
"file_too_large" without following the example links.

Root cause: `CalculateErrorSignature` (`internal/analyzer/errors.go:11-26`) produces a
16-char hex SHA256 hash from `toolName + ":" + first100chars(errorText)`. This hash becomes
the `ErrorTypeGroup.Signature` key used for grouping in `AnalyzeErrors()`
(`internal/analyzer/errors_analysis.go:85-95`). The SHA is deterministic for deduplication
but opaque to humans.

## Proposal

Add a `ClassifyErrorType(toolName, errorText string) string` function in
`internal/analyzer/errors.go` that maps error text to human-readable category labels using
regex/substring rules. Add a `Label` field to `ErrorTypeGroup` and group by label instead of
SHA. Preserve the SHA `Signature` field as a secondary key for backward compatibility.

Error classification rules (first-match, applied in order):
1. empty error with status=error → `tool_error_no_message`
2. `/exit status \d+/` → `bash_exit_code`
3. `/command not found/` → `command_not_found`
4. `/permission denied/` → `permission_denied`
5. `/no such file|file not found|ENOENT/` → `file_not_found`
6. `/connection refused|timeout|ECONNREFUSED/` → `connection_error`
7. `/parse error|syntax error|invalid.*json|unmarshal/` → `parse_error`
8. `/too large|exceeds limit|content too long/` → `content_too_large`
9. `/unauthorized|authentication|403|401/` → `auth_error`
10. `/not found|404/` → `resource_not_found`
11. fallback → `uncategorized`

This follows the established pattern: `by_tool` already groups by `tc.ToolName` (a direct
human-readable string), proving the grouping-by-label approach works.

## Plan

### Phase 1: Add classification function
- **File:** `internal/analyzer/errors.go` (after line 26, alongside `CalculateErrorSignature`)
- Add `ClassifyErrorType(toolName, errorText string) string` with the 11-rule cascade
- Use Go `regexp.MustCompile` for each pattern (compiled once at package level)
- Unit tests in `internal/analyzer/errors_test.go` for each classification rule

### Phase 2: Extend ErrorTypeGroup and update grouping
- **File:** `internal/analyzer/errors_analysis.go`
- Add `Label` field to `ErrorTypeGroup` struct (line 18):
  ```go
  type ErrorTypeGroup struct {
      Label     string   `json:"label"`
      Signature string   `json:"signature"`
      Count     int      `json:"count"`
      Examples  []string `json:"examples"`
  }
  ```
- In `AnalyzeErrors()` (line 85-95): call `ClassifyErrorType(tc.ToolName, tc.Error)` to get
  the label; use label as the grouping key; merge groups with the same label
- `Signature` (SHA) remains populated for backward compatibility and debugging
- Sort by `Count` descending, then by `Label` (replacing sort-by-Signature)

### Phase 3: Update tests
- **File:** `internal/analyzer/errors_test.go` — new tests for `ClassifyErrorType`
- **File:** `internal/analyzer/errors_analysis_test.go` — update to verify `Label` field
  presence and correctness in output
- Run `make commit` to validate

### Phase 4: Verify backward compatibility
- Existing callers of `CalculateErrorSignature` in `bugs_analysis.go`, `patterns.go`, and
  `query/context.go` are unaffected — they use SHA for internal deduplication, not the
  `ErrorTypeGroup` struct used in the public `by_type` output
- No tool schema change needed (same `analyze_errors` tool, same parameters)
