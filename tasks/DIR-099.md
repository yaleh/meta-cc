## Finding

Structural root cause from the 2026-07-30 dogfooding session: DIR-018 (done) fixed skip-and-report tolerance in the analysis `loadData` path, but that behavior was lost/not propagated when DIR-032/DIR-034 rewrote and re-wired the ListSessions path behind `query_sessions` — a corrupt file (`8eda8f4e-2c74-4176-ba6b-8c45e890df42.jsonl`, empty/truncated) hard-crashed `query_sessions` twice. There is NO mechanical enforcement that every session-corpus-consuming tool tolerates malformed files.

This is the same declared-but-not-wired drift class that DIR-041..DIR-045 addressed for schema parameters, and that DIR-045 crystallized into a static gate. The tolerance contract lives in DIR-018's precedent and DIR-094 (sibling); this task crystallizes it into a regression gate that covers every corpus-consuming tool mechanically, so the next ListSessions-style rewrite cannot silently drop tolerance again.

## Dependencies

DIR-094 (sibling task) should land first — this gate codifies that contract.

## Plan

1. Build a shared corrupt-corpus fixture in `internal/testutil/`: one empty file, one truncated JSONL, one wrong-shape file.
2. Add a table-driven regression test that runs EVERY session-corpus-consuming tool against the fixture and asserts "non-empty result + warning naming the bad file".
3. Structure the table so any newly added tool is registered in one place (one registry entry per tool, named).
4. Verify the test runs under `go test -short` (the `make commit` path) within a few seconds.
5. Negative demonstration: add a scratch tool that lacks tolerance, show the test fails for it, then remove the scratch tool.
6. Document how to register a new corpus-consuming tool in the table.

## Evidence

`internal/mcp/executor/corpus_tolerance_test.go` — one registration table (`corpusToolCases`, 10 entries) plus `nonCorpusTools` (6 entries with a written reason each), and three tests:

- `TestCorpusTolerance_CorruptSiblingsChangeNothing` runs each registered corpus-consuming tool twice over ONE seeded project — first with the DIR-094 malformed siblings, then after removing them in place — and requires the two responses to be byte-identical once `warnings` and the volatile `file_ref.path` are set aside. One project rather than two, because every session-derived record echoes its `cwd`, so a second temp project would have made the comparison partly a test that two temp dirs differ.
- `TestCorpusTolerance_EveryRegisteredToolIsClassified` reads `specialToolRegistry` ∪ `queryHandlerRegistry` from the live maps and requires every name to appear in exactly one table. This is the "one registration point" AC: a new tool that is registered but not classified fails here.
- `TestCorpusTolerance_ClassifierRejectsAnUnclassifiedTool` is the non-vacuity guard for it — a classifier that matched nothing would otherwise let the coverage test pass while enforcing nothing.

The gate distinguishes two contracts rather than pretending one fits all. `exclusionContract` (7 tools: `query_sessions`, `get_timeline`, and the six analysis tools) is DIR-018/DIR-094's "skip the whole file AND name it": the healthy session's data must still be returned, every excluded file must be named, and the clean corpus must report no exclusions at all (so a tool that names every file indiscriminately cannot satisfy it). `streamingContract` (3 tools: `query_session_content`, `query_session_signals`, `query_file_activity`) is the shared `dispatchProviderQuery → StreamFilesWithTimeRange` path, which streams records line by line and never makes a whole-file decision — a truncated line is skipped and the rest of the file still contributes, so there is no excluded file to name and DIR-094's per-path list correctly did not include them. That these three tolerate was measured, not assumed: their responses are identical with and without the corrupt siblings, and `warnings` is empty in both runs.

`query_file_activity` carries `emptyCorpusReason` instead of a marker: its selector (`file-history-snapshot` records with a `messageId`) matches nothing in the fixture, so the corpus returns zero records either way and only the no-error and control-equality halves are exercisable. An entry may leave `healthyMarker` empty only by writing that reason, so the exemption is a reviewed statement rather than an omission; `classifyCorpusTools` enforces the exclusive-or.

**Negative demonstration** (AC 1), performed against a scratch handler and then removed (`git status` clean of it). Swapping the already-registered `analyze_errors` handler for a fail-fast one — the DIR-032/DIR-034 drift shape — failed the gate with the original bug's own error text:

A second variant that tolerates *silently* (returns the result, names nothing) also failed, proving the naming half is live rather than satisfied by accident:

And an unregistered scratch tool failed the coverage check with `scratch_intolerant_tool is registered but appears in neither corpusToolCases nor nonCorpusTools`.

**Fixture** (AC 4): `tests/fixtures/malformed-corpus/` holds `healthy.jsonl` (3776 B) plus all three corruption shapes — `empty.jsonl` (0 B), `malformed.jsonl` (147 B, truncated mid-JSON), `stub.jsonl` (275 B, valid JSON with no message entries). All three are asserted per `exclusionContract` tool, driven off `testutil.MalformedCorpusExcludedNames()`.

### Touches correction: `docs` declared nothing

The original bullet `docs` was a bare directory name, and the matcher compiles a wildcard-free entry to `^docs$` — so it declared nothing *under* `docs/`, and this task's two doc writes read as out-of-declared. Measured against the real matcher:

| declared | `docs/guides/testing.md` | `docs/reference/corpus-tolerance-gate.md` |
|---|---|---|
| `docs` | no | no |
| `docs/*` | no | no |
| `docs/**` | yes | yes — but rejected as `overbroad-declaration` |

`isOverbroadDeclaration` rejects a wildcard segment unless at least two concrete segments precede it, so `docs/**` is refused even though it matches. The declaration is therefore the two files actually written, which is also the more useful statement (`docs/**` would have said the whole tree is this task's write surface). The check reads `## Touches` from the **worktree's** `tasks/<id>.md`, not from the store, so the correction had to reach the task branch as well as the board.
