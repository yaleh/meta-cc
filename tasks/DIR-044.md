## Finding

Every MCP tool built through `StandardToolParameters()` (`internal/mcp/tools/tools.go:16-17`,
merged into each tool's schema at line 106's loop, so it applies uniformly across all 16 tools —
`query_session_content`, `query_session_signals`, `query_sessions`, `query_file_activity`,
`analyze_errors`, `analyze_bugs`, `quality_scan`, `get_work_patterns`, `get_timeline`,
`get_tech_debt`, `get_session_directory`, `inspect_session_files`, `query_edit_sequences`,
`get_session_metadata`, and others) declares:

```go
// internal/mcp/tools/tools.go:44-47
"output_format": {
	Type:        "string",
	Description: "Output format: jsonl or tsv (default: jsonl)",
},
```

This is read into the pipeline config exactly once:

```go
// internal/mcp/executor/executor.go:39
OutputFormat: GetStringParam(args, "output_format", "jsonl"),
```

and stored on `PipelineConfig`:

```go
// internal/mcp/pipeline/pipeline.go:34
OutputFormat            string
```

A repo-wide grep for every place this value could plausibly be consumed — its own name, the field
name, or a TSV formatter — turns up only these same three declaration/assignment sites, never a
read:

```
$ grep -rn "OutputFormat\|output_format\|\"tsv\"\|FormatTSV\|ToTSV" internal/mcp/ --include=*.go | grep -v _test
internal/mcp/executor/executor.go:39:		OutputFormat:            GetStringParam(args, "output_format", "jsonl"),
internal/mcp/tools/tools.go:44:		"output_format": {
internal/mcp/pipeline/pipeline.go:34:	OutputFormat            string
```

`pipeline.BuildResponse` (`internal/mcp/pipeline/pipeline.go:53` onward), the function that
actually serializes and returns the tool's response body, never branches on `pc.OutputFormat`
anywhere in its body — it always calls the JSON/JSONL-producing paths
(`BuildStatsOnlyResponse`/`InjectWarnings`/etc.) regardless of what the caller requested. The one
existing test that mentions `output_format`, `internal/mcp/tools/tools_test.go:16`, only asserts
that the schema *declares* the property name — no test anywhere asserts that a TSV-formatted
response is actually produced.

**Reproduced live** against this project's own session history (`/home/yale/work/meta-cc`,
2026-07-28):

```
query_sessions({provider: "claude", output_format: "tsv", limit: 2})
```

returned a plain JSON object (`{"data":[{...},{...}],"mode":"inline","pagination":{...},"warnings":[]}`)
— standard JSONL/JSON shape, no tab-separated rows, no header line, no different `mode` field
indicating TSV was honored. The caller has no way to know their `output_format: "tsv"` request was
silently discarded; the tool schema's own description ("Output format: jsonl or tsv") promises
behavior that has never been implemented for any of the 16 tools that expose it.

This is a third instance of the same underlying defect class already fixed twice on this exact MCP
surface — a schema-declared parameter that is read into a config struct and then never consulted
by the response builder: `tasks/DIR-041.md` (`jq_filter`, fixed in commit `24d69dd`) and
`tasks/DIR-042.md` (`stats_only` on 5 of 6 analysis tools, filed and ready but not yet built). This
finding is `output_format`, a fourth distinct parameter, and the broadest in scope of all of them —
it is declared on every one of the 16 tools via `StandardToolParameters()`, not just the four
consolidated query tools or the six analysis tools.

## Proposal

1. Either implement TSV serialization in `pipeline.BuildResponse` (or a wrapper around its return
   value) — converting the flat/near-flat JSON records each tool already produces into
   tab-separated rows with a header line when `pc.OutputFormat == "tsv"` — or, if TSV output is not
   actually planned/supported, remove `output_format` from `StandardToolParameters()` and its
   documentation so it stops advertising a capability that has never existed.
2. Whichever direction is chosen, add a regression test that fails today: a call with
   `output_format: "tsv"` must produce a response structurally distinguishable from the same call's
   JSONL output (if implemented), or the parameter must be rejected/absent from the schema (if
   removed) — not silently ignored.
3. Audit `docs/guides/mcp-query-tools.md` and any other documentation referencing `output_format`
   so the documented contract matches whichever behavior is implemented.
