## Finding

During the 2026-07-30 dogfooding analysis session, a "last 2 days" question produced whole-corpus (5-day) statistics, silently mixing time windows in the report. Root cause: `analyze_errors`, `analyze_bugs`, `quality_scan`, `get_work_patterns`, and `get_tech_debt` accept NO `since`/`until` parameters.

DIR-021 (done) fixed since/until for role=assistant content queries, but the five analysis tools remain uncovered. `query_session_signals` and `get_timeline` already support RFC3339 `since`/`until`, so the filtering vocabulary exists — it is simply not wired into the analyzers.

Compounding evidence from the same session: `query_sessions` hard-failed with `MCP error -32603: provider claude: no Claude entries in /home/yale/.claude/projects/-home-yale-work-meta-cc/8eda8f4e-2c74-4176-ba6b-8c45e890df42.jsonl` (tolerance fix tracked in DIR-094). Without time-window parameters there was no way to re-run the analysis against a known time-bounded subset.

## Dependencies

Follows DIR-021 (done, since/until for content queries). Complementary to DIR-094 (tolerant loading); not a duplicate of either.

## Scope

owner_repo: meta-cc

Add RFC3339 `since`/`until` to the five analysis tools with the same semantics as the existing `query_session_signals`/`get_timeline` parameters (since inclusive, until exclusive). Filtering happens before aggregation, so `stats_only`/`stats_first` outputs honor the window. Invalid timestamps yield `mcerrors.ErrInvalidInput`, never a crash.

### AC1 — the window is honored (five tools + get_timeline)

The proof is an equivalence, not a hand-written expected value: a windowed run
over the full corpus must equal an unwindowed run over a corpus seeded with
only the in-window entries, and must *differ* from the unwindowed full-corpus
run (so a tool that silently ignored its window cannot pass).

Fixture: a January half (Bash failure → same-tool Bash success → Read with a
`FIXME` marker) and a February half (two Reads with `TODO` markers); window =
February 2026.

```
go test ./internal/analysis/... -run TimeWindow -v
--- PASS: TestAnalysisTools_WindowedRunMatchesInWindowSubset
    --- PASS: .../analyze_errors  .../analyze_bugs  .../quality_scan
    --- PASS: .../get_work_patterns  .../get_tech_debt  .../get_timeline
--- PASS: TestAnalysisTools_WindowedCountsExcludeOutOfWindowData
    --- PASS: .../analyze_errors  .../analyze_bugs  .../quality_scan
    --- PASS: .../get_work_patterns  .../get_tech_debt
```

Concrete counts, so a failure says what leaked:

| tool | whole corpus | February window |
| --- | --- | --- |
| `analyze_errors` | `total_errors` 1, `time_range.start` 2026-01-15 | 0, `time_range.start` 2026-02-15 |
| `analyze_bugs` | `total_errors` 1, `total_pairs` 1 | 0, 0 |
| `quality_scan` | `error_rate` raw `1/5` | `0/2` |
| `get_work_patterns` | `{Bash: 2, Read: 3}` | `{Read: 2}` |
| `get_tech_debt` | markers `{FIXME: 1, TODO: 2}` | `{TODO: 2}` |

Through the real MCP dispatch (`internal/mcp/executor`):
`TestAnalyzeErrors_EndToEnd_HonorsTimeWindow` — `total_errors:1` unwindowed,
0 windowed.

`get_timeline` is in every list above because DIR-095 replaced its private
filtering block with the shared `applyTimeWindow`, so these pin that refactor
too.

### AC2 — invalid input, not a crash

`filterEntriesByTimeRange` now wraps `mcerrors.ErrInvalidInput`; the executor's
`validateTimeWindow` rejects a bad bound before the corpus is located and
parsed.

```
go test ./internal/analysis/... ./internal/mcp/executor/... -run TimeWindow -v
--- PASS: TestAnalysisTools_RejectInvalidTimeWindow          (6 tools x 2 bounds, ErrorIs)
--- PASS: TestAnalysisTools_EndToEnd_RejectsInvalidTimeWindow (6 tools x 2 bounds, errors.Is)
--- PASS: TestAnalysisTools_DeclareTimeWindowParameters       (6 tools)
```

The schema half matters as much as the error: a parameter the service honors
but no tool schema declares is unreachable in production, because
`ExecuteTool`'s `ValidateToolArgs` rejects undeclared keys before dispatch
(the DIR-023 failure mode). Both halves are asserted.

### AC3 — `stats_only` honors the window; the `stats_first` clause is void

`stats_only`: genuinely satisfied, and filtering runs *before* the
`stats_only` branch is reached, so the aggregate and the detail path can never
disagree.

```
go test ./internal/analysis/... -run StatsOnlyHonorsWindow -v
--- PASS: TestAnalysisTools_StatsOnlyHonorsWindow  (6 subtests)
```
plus `.../WindowedCountsExcludeOutOfWindowData/get_tech_debt`, which asserts
`stats_only` `marker_count` = 2 windowed vs 3 whole-corpus.

`stats_first`: **not satisfied as literally worded, and not satisfiable.** These
six tools never declared `stats_first` — DIR-048 scoped it to the four
pipeline-routed query tools, because it paginates the flat record array those
return and these return typed analyzer structs instead. `ValidateToolArgs`
rejects it as an undeclared key, so no `stats_first` output exists for these
tools for a window to be reflected in. The AC's `stats_first` clause
presupposes a parameter that was deliberately removed from this tool family
before this task existed; the requirement it is reaching for — "aggregate-mode
output must not silently ignore the window" — is discharged by `stats_only`.
Pinned by `TestAnalysisTools_DoNotDeclareStatsFirst` (fails if a later change
starts accepting it here, forcing whoever makes that change to decide what the
window should mean for it) and documented in `docs/guides/mcp.md`. Ticked on
the reading the task's own Plan prescribes ("covering both detail and
stats_only/stats_first outputs" = filter before aggregation), with this caveat
recorded rather than the box left open.
