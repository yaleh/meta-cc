## Finding

DIR-032 built `codex.Provider.ListSessionsPage(ctx, filter, cursor) (SessionPage, error)` (`internal/provider/codex/provider.go:223-248`) specifically as, in its own doc's words, "**A cursor-based continuation API for callers**" (`docs/reference/codex-history-model.md:187-198`) that "fetches exactly one real `thread/list` page when app-server is reachable ... returning the server's own `nextCursor`" — i.e. bounded, page-at-a-time listing instead of walking an entire corpus.

It has **zero production callers**. A repo-wide search confirms every non-test reference is internal to the `codex` package itself:

```
$ grep -rln "ListSessionsPage" --include=*.go . | grep -v _test.go
internal/provider/codex/appserver/version.go
internal/provider/codex/appserver_provider.go
internal/provider/codex/provider.go
```

The only two test files that exercise it (`internal/provider/codex/provider_dispatch_test.go`, `internal/provider/codex/appserver_provider_test.go`) are both inside `internal/provider/codex` — no MCP-layer test, and no `internal/mcp/executor` code path, ever calls it.

The one MCP tool that lists session metadata, `query_sessions` (`internal/mcp/executor/query_sessions_handler.go:handleQuerySessions`), does **not** use `ListSessionsPage`. Instead, at line 111 it calls `p.ListSessionsFiltered(ctx, filter)`, which (`internal/provider/codex/appserver_provider.go:198-243`, `listSessionsFiltered`/`listAll`) always pages the underlying `thread/list` **to completion** for every requested archived pass before returning — `listAll`'s own doc comment says it "follows thread/list pagination (cursor/nextCursor) to completion for one archived-state pass." `handleQuerySessions` then applies `limit` as a purely client-side slice *after* that full fetch (`query_sessions_handler.go:150-152`):

```go
conversation.SortSessionsDeterministic(merged)
if limit := GetIntParam(args, "limit", 0); limit > 0 && len(merged) > limit {
    merged = merged[:limit]
}
```

So `query_sessions(provider="codex", limit=1)` against a large Codex corpus performs exactly as many `thread/list` app-server round-trips as an unlimited query — the bounded single-page API exists but is never reached, defeating the stated purpose of building it (this is exactly the "hundreds of sessions" scaling concern DIR-031/DIR-032 were themselves motivated by).

This differs from DIR-031's FTS index, which explicitly discloses its own similar situation in `docs/reference/fts-index.md`'s "Known limitations" section ("Not wired into an MCP tool or CLI flag yet ... Wiring is a small, mechanical follow-up"). `docs/reference/codex-history-model.md`'s "Known limitations / explicitly out of scope (DIR-032, first pass)" section (lines 240-255) discusses `ListSessionsPage`'s internal archived-filter semantics as if it is an in-use API, but never states that it has no caller — an undisclosed gap between what the reference doc implies is delivered and what MCP callers can actually reach.

## Proposal

Either wire `query_sessions` to actually use `ListSessionsPage` for bounded, incremental fetching (accepting/returning a `cursor` so a caller with `limit` set doesn't force a full corpus crawl), or, if that wiring is deliberately deferred, explicitly disclose the gap in `docs/reference/codex-history-model.md`'s "Known limitations" section the same way DIR-031 did for `internal/ftsindex`, so the reference doc doesn't imply `ListSessionsPage` is an in-use capability when today it is dead code from the MCP surface's perspective.

## Contract

- `docs/reference/codex-history-model.md` accurately reflects whether `ListSessionsPage` has a real caller at the time it is read — no reference doc describes an unused capability as delivered "for callers" without saying so.
- If wired: `query_sessions(provider="codex", limit=N)` for small `N` against a large corpus does not require paging through every `thread/list` page before returning — verified by a test asserting the number of `thread/list` calls the fake `threadSource` receives is bounded by the requested `limit`/page count, not by total corpus size.
- If not wired (disclosure-only fix): no functional code changes; the doc update alone must not misrepresent test coverage or claimed capability.
- Existing `query_sessions` behavior (filters, cwd boundary, sort order, `offset`/`page_size` pipeline pagination) is unchanged for callers that don't ask for bounded/cursor fetching.

## Plan

1. Decide between the two remediation paths (wire vs. disclose) — wiring is preferred if it fits DIR-032's original line-budget precedent; disclosure-only is the minimal fix.
2. If wiring: add an internal loop in `handleQuerySessions`'s codex branch that calls `p.ListSessionsPage` repeatedly, stopping once `limit` results are collected (when `limit > 0`) or a page returns an empty `NextCursor`, instead of calling `p.ListSessionsFiltered`.
3. Add a regression test with a fake `threadSource` that fails the test if more `thread/list` calls occur than are needed to satisfy a small `limit`.
4. Update `docs/reference/codex-history-model.md` to describe the actual, current caller relationship (either "now used by query_sessions for bounded fetches" or an explicit "Known limitations" entry mirroring `fts-index.md`'s wording).
5. Re-verify `query_sessions`'s existing filter/sort/cwd-boundary tests still pass unchanged.
