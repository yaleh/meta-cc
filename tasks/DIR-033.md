## Finding

The identical defect shape — an unscoped, global `locator.SessionLocator.FromSessionID(sessionID)` call that resolves a session file by ID across every project-hash directory on disk with **no comparison against the caller's `working_dir`/cwd** — was independently introduced and independently caught **three separate times** in this repo's own recent history, all traceable in this project's own Claude Code session logs:

1. **`internal/mcp/executor/provider_query.go:66`**, `ExecuteQueryForSession` (Claude/default provider branch) — found and fixed during DIR-030's landing. Evidenced in session `eb482896-9962-4f8e-8fc0-8b63100bbaf6` (2026-07-26, `task_get`/`gate_run` turns ~00:58–01:29 UTC), which discusses "`provider==""`/`"claude"` (the DEFAULT, most-used path) → instead calls `locator.NewSessionLocator().FromSessionID(sessionID)` ... with **zero comparison against the caller's `working_dir`/cwd**."
2. **`internal/provider/claude/provider.go`'s `findSessionFile`** — found and fixed proactively during the DIR-032 build itself, in the same worktree/branch (`milestones/meta-cc/DIR-032`), before the diff was even reviewed.
3. **`internal/analysis/service.go:105-110`**, `loadData`'s `case sessionID != "":` branch — found by a fresh-context adversarial audit AFTER the DIR-032 build claimed (at the commit-message level) to have closed this bug class system-wide. Reproduced independently by the auditor: seeded two project-hash directories (project A empty, project B containing a session with distinguishable secret content), called `AnalyzeErrors({"working_dir": projectA, "session_id": "<project-B-session>"})`, and it returned project B's content. This is reachable from **six shipped MCP tools** that all go through `analysis.Service.loadData`: `analyze_errors`, `analyze_bugs`, `quality_scan`, `get_work_patterns`, `get_timeline`, `get_tech_debt`. Evidenced in session `b05a930b-8d45-42d8-98db-918c4fad6ade` (this repo's current session, `task_get`/`task_write`/`gate_run` turns 2026-07-27T15:57–19:08 UTC), which records the "needs-human: adversarial audit REFUTATION FOUND" verdict now appended to `tasks/DIR-032.md`.

All three are now fixed on `main` (commit `2f93b73`), each with the same repeated hand-written fix shape: resolve via `FromSessionID`, then compare `filepath.Base(filepath.Dir(sessionFile))` (or an equivalent) against `locator.PathToHash(workingDir)`, erroring/excluding on mismatch.

**A fourth, still-live call site exists today** (independently verified by this probe, not just taken from the DIR-032 audit's word): `internal/locator/locator.go:25`, inside `(*SessionLocator).Locate(opts LocateOptions)`, calls `l.FromSessionID(opts.SessionID)` with the same zero-comparison-to-cwd shape. A repo-wide grep (`grep -rn "\.Locate(\|LocateOptions{" --include=*.go .` excluding `_test.go` and `locator.go` itself) found **zero production callers** of `Locate`/`LocateOptions` anywhere in the repo — it is dead code from an old CLI-flag era (`--session`/`--project`, "Phase 13" per its own Chinese-language doc comments), not currently reachable through the MCP surface. It is not a live leak today, but it is a landmine: the exact same bug shape, sitting unfixed, ready to become live again the moment someone wires a caller to it, or copies its pattern into a new call site — which is exactly how instances 2 and 3 above were introduced in the first place.

**Root cause is structural, not a one-off typo**: `locator.SessionLocator.FromSessionID(sessionID string)` is a low-level primitive with no `workingDir` parameter and no way to fail closed on a cross-project match — every caller must remember, unprompted, to add a `PathToHash` boundary check afterward. Three different build/fix passes over ~2 days (2026-07-25 through 2026-07-27) each had to rediscover and hand-roll this same check. There is currently no static gate, lint rule, or test that would catch a fifth introduction of this pattern (e.g., a new MCP tool or CLI path calling `FromSessionID` directly without the boundary check).

## Proposal

Crystallize the three repeated ad-hoc boundary checks into one primitive that makes the mistake structurally impossible, and add a regression gate that fails the build if `FromSessionID` is ever called again without going through it:

1. Add a new method, e.g. `(l *SessionLocator) FromSessionIDScoped(sessionID, workingDir string) (string, error)`, that internally calls `FromSessionID` and then performs the `PathToHash(workingDir)` boundary comparison exactly once, returning a "not found for project" error on mismatch (matching the error shape already used in `service.go` and `provider_query.go`).
2. Migrate all three now-fixed call sites (`provider_query.go`, `provider.go`'s `findSessionFile`, `analysis/service.go`'s `loadData`) to call the new scoped method instead of duplicating the boundary-check logic inline.
3. Either delete the dead `Locate`/`LocateOptions` code in `internal/locator/locator.go` (confirmed zero production callers), or, if it is being kept for a planned CLI reintroduction, migrate its `FromSessionID` call to `FromSessionIDScoped` too so it isn't a live landmine.
4. Add a static/CI-time grep gate (a small script or a `go vet`-style check invoked from `make commit`/`make push`) that fails if any `.go` file outside `internal/locator/` calls `.FromSessionID(` directly — the only sanctioned caller of the raw, unscoped primitive should be `FromSessionIDScoped` itself.

## Contract

- Every code path that resolves a `session_id` string to a file on disk enforces the caller's `working_dir`/cwd boundary — no exceptions, no per-callsite reimplementation.
- `FromSessionID` (raw, unscoped) is only ever called from within `internal/locator/` itself; all external callers use `FromSessionIDScoped`.
- The CI gate fails loudly (not silently) if a new unscoped `FromSessionID(` call site is added anywhere else in the tree.
- No behavior change for legitimate same-project session lookups — only cross-project lookups are newly/consistently rejected.
- Dead code (`Locate`/`LocateOptions`) is either removed or brought into compliance with the same boundary contract — it does not linger as an unscoped landmine either way.

## Plan

1. Add `FromSessionIDScoped` to `internal/locator/args.go` (or `locator.go`), with a table-driven test mirroring the existing `TestFromSessionID_MultipleProjects` fixture plus an explicit cross-project-rejection case.
2. Refactor `internal/mcp/executor/provider_query.go`, `internal/provider/claude/provider.go` (`findSessionFile`), and `internal/analysis/service.go` (`loadData`) to call `FromSessionIDScoped`, deleting the now-duplicated inline `PathToHash` comparisons.
3. Decide and act on `internal/locator/locator.go`'s dead `Locate`/`LocateOptions`: remove it, or route its `FromSessionID` call through `FromSessionIDScoped`.
4. Add a `make`-invoked grep/lint gate (e.g. `scripts/gates/` or a `go test` that shells out to `grep`) asserting `FromSessionID(` appears only inside `internal/locator/`.
5. Run `make commit` and confirm the new gate fails on a deliberately reintroduced unscoped call (verify the gate actually catches the bug class, don't just add a script that never fires), then remove the deliberate regression before landing.
