# `query_session_signals` outcome filters (`status`, and the pre-existing `type="errors"`) silently drop ~97% of records under `provider="all"`

## Finding

DIR-043's adversarial audit (fresh-context, independent reproduction) discovered that the newly-fixed
`status` filter on `query_session_signals(type="tool_stats")`, and the pre-existing, already-shipped
`query_session_signals(type="errors")` handler (`handleQueryToolErrors`,
`internal/mcp/executor/handlers.go`), both degenerate badly under `provider="all"`.

**Reproduced live** against this project's own session history (`/home/yale/work/meta-cc`,
2026-07-28), built `cmd/mcp-server` and drove it over stdio JSON-RPC:

- Default provider (`"claude"`): `query_session_signals(type="tool_stats", status="error")` and
  `status="success"` correctly partition the unfiltered total (122 + 5778 = 5900 ≤ 5901 unfiltered —
  the 1-record gap is a single in-flight tool_use with no observed result yet, which is the
  documented, intended exclusion).
- Under `provider="all"` — the exact mode `tasks/DIR-043.md`'s own `## Finding` section used to
  derive its "312/7-session/44-bucket" baseline — `status="error"` returns **0 records**, and
  `status="success"` returns only **10 of 322** total records (matching only 1 of 7 sessions). ~97%
  of tool_use records are silently excluded from *both* branches, with no warning, error, or `has_more`
  signal indicating anything was dropped.
- Root cause (per the audit): this is a **pre-existing, unrelated defect** in
  `providerrecords.Build`'s canonicalized/normalized record shape (used by the `provider="all"` path)
  being incompatible with the raw-JSONL-shaped jq filters and Go-side `tool_use_id` correlation logic
  both `handleQueryTools` and `handleQueryToolErrors` rely on — it is not something DIR-043 introduced;
  `handleQueryToolErrors` (`type="errors"`) exhibits the identical degeneracy on the same project
  history today, independent of the DIR-043 diff.

This means any caller combining `provider="all"` (documented and commonly used elsewhere in this
codebase — see `CLAUDE.md`'s own FAQ examples using `provider: "all"`) with either of these two
outcome-filtering signal types gets a silently near-empty, misleading result instead of the correct
cross-provider filtered set.

## Proposal

1. Root-cause why `providerrecords.Build`'s canonical/normalized records (used under `provider="all"`)
   don't correlate correctly with the `tool_use`/`tool_result` join logic in `handleQueryTools` and
   `handleQueryToolErrors` — likely a mismatch between the raw Claude JSONL shape these jq
   filters/Go correlation code expect, and the normalized cross-provider record shape actually
   produced for `provider="all"`.
2. Either fix the join/filter logic to work correctly against the normalized `provider="all"` record
   shape, or explicitly detect the `provider="all"` + outcome-filter combination and either warn in
   the response (e.g. a `warnings` entry) or fail closed with an actionable error rather than
   returning a silently near-empty result.
3. Add a regression test that reproduces the specific degeneracy: a `provider="all"` fixture spanning
   multiple providers/sessions, exercising both `type="tool_stats"` with `status` set and
   `type="errors"`, asserting the filtered count is NOT near-zero when matching records exist across
   more than one session/provider.
