# quality_scan dimensions are mathematically degenerate: completion_rate ≡ 1−error_rate (tautology), tool_diversity → 0 as activity grows

## Finding

`QualityScan` (`internal/analyzer/quality_analysis.go:23-95`) reports four
"quality dimensions" documented as `"Score 0.0–1.0 (higher = better quality)"`
(line 7). Two of the four are degenerate:

**1. completion_rate is exactly 1−error_rate for every possible input.**

```go
// quality_analysis.go:39-45 (error_rate)
if tc.Status == "error" || tc.Error != "" { errors++ }
errorScore := 1.0 - float64(errors)/float64(total)

// quality_analysis.go:77-84 (completion_rate)
if tc.Status == "success" || (tc.Status == "" && tc.Error == "") { successes++ }
completionScore := float64(successes) / float64(total)
```

These two conditions are exact complements over every `ToolCall` (Status is
"error", "success", or "" — and the "" case is split by `Error` identically in
both), so `successes ≡ total − errors` and `completionScore ≡ errorScore` always.
Live proof (mined 2026-07-28 from session
`16c504aa-6681-40b0-bfce-4f25f4dce679`):

```
quality_scan({scope:"project"}):
  {"name":"error_rate",      "score":0.9818409517845961, "raw_value":"29/1597"}
  {"name":"completion_rate", "score":0.9818409517845961, "raw_value":"1568/1597"}
  (1568 = 1597 − 29; scores byte-identical to 16 decimal places)

quality_scan({session_id:"2a38491e-8724-4119-b3c7-6b12230216eb"}), three runs:
  error_rate 0.9712230215827338 (4/139) ≡ completion_rate 0.9712230215827338 (135/139)
```

DIR-002 (done) fixed completion_rate "always reports 0" — that bug came from
`Status` always being "" pre-normalization; commit e3d070c ("normalize
ToolCall.Status from IsError") fixed the counting but silently turned the
dimension into a tautological clone of error_rate. Half of the quality dashboard
carries zero independent information.

**2. tool_diversity = unique_tools / total_calls monotonically *decreases* as a
project does more work** — the opposite of "higher = better quality".

```go
// quality_analysis.go:67-75
unique := make(map[string]struct{})
for _, tc := range toolCalls { unique[tc.ToolName] = struct{}{} }
diversityScore := float64(len(unique)) / float64(total)
if diversityScore > 1.0 { diversityScore = 1.0 }   // <- unreachable: unique ≤ total always
```

The numerator is bounded by the finite tool universe (~40–60 tools exist in
Claude Code), while the denominator grows without bound, so every active project
converges toward score 0 regardless of quality. Live proof:

```
quality_scan({scope:"project"}):   tool_diversity score 0.0244  raw "39/1597"  (healthy active project)
quality_scan({session 2a38491e}):  tool_diversity score 0.1367  raw "19/139"   (one session)
quality_scan on a 1-call session:  score 1.0                                   ("perfect")
```

A one-tool-call session scores "perfect quality" on four dimensions (the `total==0`
and single-call paths return vacuous 1.0s), while sustained, varied, low-error work
scores 0.024 on diversity. The existing test codifies the formula instead of the
intent: `internal/analyzer/quality_analysis_test.go:94-119`
(`TestQualityScan_ToolDiversity`) asserts `score == 0.5` for 2 unique tools over
4 calls, locking the degenerate semantics in place.

**Recurrence pattern:** this is the same defect class as DIR-002 (a quality metric
whose number is detached from quality) recurring in the sibling dimensions that
DIR-002 didn't audit. Every `quality_scan` call — including any self-validation
routine or gate that consumes these scores — reports two duplicate numbers and one
size-penalized number as if they were independent quality signals.

Not a duplicate: DIR-002 covered only completion_rate's then-always-0 behavior
(fixed); no task DIR-001..DIR-057 mentions the completion≡error tautology or the
diversity saturation curve (grep of `tasks/*.md` for "diversity" = zero hits).

## Proposal

1. **completion_rate:** either (a) delete the dimension and document the removal,
   or (b) make it measure something distinct — e.g. fraction of tool calls that
   produced a tool_result at all (completion in the literal sense:
   `Status != ""`), which today is *not* identical to non-error because calls
   with `Status=="" && Error==""` (no observed result) count as "success".
   Pick (a) or (b); if (b), add a fixture proving the two scores differ when a
   tool_use has no tool_result.
2. **tool_diversity:** replace the ratio with a size-independent measure — e.g.
   Shannon entropy of the tool-call distribution normalized by ln(unique) (1.0 =
   perfectly even usage across the tools actually used), or simply report the raw
   `unique` count with `Score` removed/nullable for this dimension. Whatever is
   chosen, the score must not decrease when additional (non-error) tool calls of
   existing tools are appended.
3. Delete the unreachable `if diversityScore > 1.0` clamp.
4. Update `TestQualityScan_ToolDiversity` to assert the *intent* (e.g. score
   invariant under appending more calls of already-used tools; or monotonic in
   genuine evenness), and add `TestQualityScan_CompletionNotTautological` proving
   completion and error scores differ on a fixture containing a tool_use with no
   tool_result (if option (b) is chosen).
