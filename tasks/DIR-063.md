# Codex sqlite extractTime maps TEXT/zero timestamps to 1970 (never zero), silently defeating the created_at fallback chain

## Finding

`extractTime` in the Codex SQLite reader never returns the zero time for a present-but-unparseable value: a TEXT timestamp is `fmt.Sscan`-parsed for a leading integer (yielding a small number → `time.Unix` → a 1970 date), and an `int64(0)` column maps to `time.Unix(0,0)`. Because the result is never `IsZero()`, the `created_at_ms → created_at` fallback chain is skipped, pinning session `CreatedAt`/`UpdatedAt` to 1970. Downstream, "most-recent session" selection and all `since`/`until` filters operate on garbage.

Source — `internal/provider/codex/sqlite.go:231-247`:
```go
func extractTime(value interface{}) time.Time {
    switch v := value.(type) {
    case int64:
        if v > 1_000_000_000_000 { return time.UnixMilli(v) }
        return time.Unix(v, 0)          // int64(0) → 1970-01-01, IsZero()==false
    case []byte:
        return extractTime(stringValue(v))
    case string:
        var iv int64
        _, _ = fmt.Sscan(v, &iv)         // "2026-07-28..." → iv=2026
        return extractTime(iv)           // → time.Unix(2026,0) → 1970-01-01T00:33:46Z
    default:
        return time.Time{}
    }
}
```
Fallback chain it defeats — `sqlite.go` (session scan): `createdAt := extractTime(colMap["created_at_ms"]); if createdAt.IsZero() { createdAt = extractTime(colMap["created_at"]) }`. Since `extractTime` of a TEXT `created_at_ms` (or a `DEFAULT 0` integer) is non-zero 1970, the real `created_at` is never consulted.

Reproduced with a standalone copy of the exact function:
```
[extractTime] "2026-07-28T10:00:00Z" => 1970-01-01T00:33:46Z  IsZero=false
[extractTime] int64(0)            => 1970-01-01T00:00:00Z  IsZero=false
```
The code explicitly handles `string`/`[]byte`, so TEXT timestamps were anticipated — and the handling is wrong for every non-numeric string. Consequences: `FilterSessionsForScope`'s most-recent-session pick (records.go) and any time-range filter see 1970; combined with second-granularity ties, "most recent" becomes effectively arbitrary.

## Proposal

1. Make `extractTime` return the zero time (or `(time.Time, bool)`) when the value is not a valid epoch number: for the `string` case, only accept a fully-numeric string (e.g. `strconv.ParseInt` over the whole string, reject on error); treat `int64(0)`/negative as "absent" (zero) so the fallback engages; try an RFC3339 parse for TEXT timestamps before giving up.
2. At the call sites, fall back on `IsZero()` (already the intent) and, if all sources are zero, leave `CreatedAt` unset rather than 1970.
3. Add a unit test covering: TEXT RFC3339 timestamp, numeric-string epoch, `int64(0)`, empty string, and a `created_at_ms DEFAULT 0` row that must fall back to `created_at`.
