## Finding

`internal/provider/codex/provider.go`'s `FetchSessionsBounded` (DIR-034's bounded/cursor-based
session-listing entry point, added in commit `88a79bf` "feat(codex): wire query_sessions to
bounded ListSessionsPage fetch") pages through `ListSessionsPage` in a loop:

```go
// internal/provider/codex/provider.go:276-300
func (p *Provider) FetchSessionsBounded(ctx context.Context, filter conversation.SessionFilter, limit int) ([]conversation.Session, error) {
	if limit <= 0 {
		return p.ListSessionsFiltered(ctx, filter)
	}

	var collected []conversation.Session
	cursor := ""
	for {
		page, err := p.ListSessionsPage(ctx, filter, cursor)
		if err != nil {
			return nil, err
		}
		collected = append(collected, conversation.ApplyFilter(page.Sessions, filter)...)
		if page.NextCursor == "" || len(collected) >= limit {
			break
		}
		cursor = page.NextCursor
	}
	...
}
```

If page 1 (and possibly pages 2..N-1) succeed and populate `collected`, but a later page fetch
fails, the function returns `nil, err` — discarding every session already collected in `collected`
— instead of returning the partial `collected` slice plus a warning.

This directly contradicts the fault-tolerance behavior already established for the *unbounded*
sibling path this same file documents just above it. `appServerBackend.listAll`
(`internal/provider/codex/appserver_provider.go:245-276`), which backs `ListSessionsFiltered`, is
explicit that "a failure AFTER at least one page already succeeded... returns the threads fetched
so far plus a recorded warning... instead of discarding them, so a genuine mid-pagination blip
degrades gracefully rather than causing whole-corpus loss" (comment at
`internal/provider/codex/appserver_provider.go:217-226`). `listSessionsPage` itself (the single-page
primitive `FetchSessionsBounded` calls) documents that its own no-partial-progress behavior is
acceptable specifically because "the caller already holds the cursor it passed in and can retry it
directly" (`internal/provider/codex/appserver_provider.go:306-310`) — i.e. the multi-page caller
(`FetchSessionsBounded`) is the one expected to preserve/retry, but it does not: it neither returns
the collected sessions nor exposes the last-good cursor to its own caller for a resume.

**Reproduced live** with a temporary test added directly to `internal/provider/codex/` (removed
after verification, not committed) using the repo's own existing `fakeThreadSource.failOnCursor`
fixture mechanism (already used by
`TestAppServerBackendListAllToleratesPageFailureMidPagination` in
`internal/provider/codex/appserver_provider_test.go`) with a 3-page fixture (page 1 succeeds, page
2's cursor is configured to fail) and `limit=3`:

```
=== RUN   TestScratchFetchSessionsBoundedDiscardsPartialOnMidPageFailure
    zzz_scratch_verify_test.go:30: FetchSessionsBounded: sessions=0 err=codex app_server backend: thread/list: boom mid-pagination
    zzz_scratch_verify_test.go:32: CONFIRMED: page 1 succeeded (1 session fetched) but FetchSessionsBounded discarded it and returned err=codex app_server backend: thread/list: boom mid-pagination with 0 sessions
--- PASS: TestScratchFetchSessionsBoundedDiscardsPartialOnMidPageFailure (0.00s)
```

(`sessions=0` even though page 1's session `t1` was successfully fetched and appended to
`collected` before page 2 failed.)

This is user-visible through the MCP surface: `internal/mcp/executor/query_sessions_handler.go:128-137`
routes `query_sessions(provider="codex", limit=N, archived=<bool>)` — a very common call
shape, since `archived` now defaults to `false` per the same DIR-032/034 landing — through
`FetchSessionsBounded` whenever `limit > 0 && scope != "session" && filter.SessionID == "" &&
filter.Archived != nil`. On a mid-pagination hiccup, the handler does:

```go
if err != nil {
	warnings = append(warnings, fmt.Sprintf("provider codex: %v", err))
	continue
}
```

turning what should be "N-1 real sessions plus a resumable-cursor warning" into "zero Codex
sessions plus an opaque error string in `warnings`" — a strictly worse outcome for the *bounded*
(supposedly more scalable) path than the *unbounded* `ListSessionsFiltered` path it was built to
replace for exactly this large-corpus case.

No existing test exercises this: `TestProviderFetchSessionsBoundedStopsEarly` and
`TestProviderFetchSessionsBoundedFallsBackWhenLimitZero`
(`internal/provider/codex/provider_dispatch_test.go:279,320`) only cover the all-pages-succeed case,
and `TestQuerySessions_Codex_LimitUsesBoundedFetchAndReturnsMostRecent`
(`internal/mcp/executor/query_sessions_handler_test.go:214`) likewise never injects a page failure.

## Proposal

Make `FetchSessionsBounded` tolerate a page failure after at least one page has already succeeded,
mirroring `listAll`'s existing contract instead of contradicting it:

1. On a `ListSessionsPage` error where `len(collected) > 0`, return the sorted/trimmed `collected`
   slice (not `nil`) plus a warning identifying the failure and the cursor to resume from, using an
   error type or a `(sessions, warning, error)`-shaped return (matching how `listAll`/
   `listSessionsFiltered` already surface warnings via `p.Warnings()`/`drainWarnings()`) rather than
   a bare `error`.
2. Only return a hard error when the very first page fails with zero sessions collected —
   preserving today's fail-fast behavior for "app-server appears to not be working at all," which
   is the same first-page-vs-later-page distinction `listSessionsFiltered` already draws.
3. Wire the returned warning through to `query_sessions`'s response `warnings` array
   (`internal/mcp/executor/query_sessions_handler.go`) alongside whatever Codex sessions were
   actually recovered, instead of the current all-or-nothing `continue`.

- [ ] A committed regression test in `internal/provider/codex/` (following the existing
      `failOnCursor` fixture pattern in `appserver_provider_test.go`) proves: page 1 of a 3-page
      fetch succeeds, page 2 fails, `FetchSessionsBounded(ctx, filter, limit=3)` returns the 1

      failure — it must NOT return an empty session slice.

      `query_sessions(provider="codex", limit=N, archived=false)` against a fixture whose Codex
